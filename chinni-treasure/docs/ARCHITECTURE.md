# Chinni Treasure — Architecture Context

Module seams, ownership rules, and the review history behind them. The domain
vocabulary these modules implement is in [CONTEXT.md](../CONTEXT.md); the decisions
that are hard to reverse are in the [ADRs](adr/).

Read this before proposing a refactor. A candidate already marked **Resolved** was
answered, with a reason — re-proposing it spends a review on a settled question.

## Architecture modules

These are **deep modules** — small interfaces, big hidden implementations — that own a concept. Future reviews should deepen around these seams, not re-litigate them.

### Catalogue cache module — *seam*
`src/lib/catalogue-cache.ts`. Owns **all six catalogue caches** (`products`, `catindex`, `categories`, `catlatest`, `catpage`, `giftboxes`) and exports `invalidateCatalogCaches()`, which clears exactly what the module owns (the namespace in Redis via SCAN+DEL **plus** the local in-memory fallback). Routes import their cache from this module; they never call `createRedisCache` themselves. **Resolved by the Aug 2026 architecture review** — do not re-suggest a hardcoded namespace list. The `catindex` cache holds the full active-product list per hostname so public catalogue searches filter in memory instead of querying Postgres per request. The index query surface (`queryCatalogueIndex`, filter/sort/page over `catindex`) lives in this module too, so the route only parses, calls, and envelopes. `SORT_OPTIONS` — the **one catalogue order contract** — lives here too: every entry is a complete orderBy (in-stock first, then the chosen field, then id desc), consumed verbatim by the `/api/products` status branch (`listProductsForQuery` in `product-read.ts`), the category pages, and the in-memory `catIndex` comparator (which walks the same arrays). Changing a sort rule means editing `SORT_OPTIONS`; no route re-declares an order. **Resolved by the Sep 2026 review** — do not re-add per-route orderBy mirrors. **The table itself now lives in `src/lib/sort-contract.ts`** (re-exported from here) so the client pickers and the OpenAPI enum can import it without dragging Prisma/Redis into the client bundle; see [Sort contract module](#sort-contract-module--seam).

### Sort contract module — *seam*
`src/lib/sort-contract.ts`. One dependency-free module owning the catalogue's sort vocabulary in full: `SORT_OPTIONS` (key → orderBy), `SORT_KEYS`, `SORT_LABELS` (typed `Record<SortKey, string>`, so a key without a label is a typecheck error), and the category page's subset `CATEGORY_SORT_KEYS` / `CATEGORY_SORT_MAP` / `CategorySortKey`. The admin catalogue `<select>`, the category page's `<select>` and the documented `sort` enum all derive from it, so a picker can no longer offer a key the route 400s. **Resolved Sep 2026 (architecture review, candidate 1).** The dashboard's `ORDER_COLUMN_SORTS` stays beside the orders columns — it is the orders API's own vocabulary, not a catalogue key.

### Admin list module — *seam*
`src/components/admin/table/AdminList.tsx` + `sort-adapter.ts`. One home for the admin tables' shared composition: `useAdminListTable` (the server-driven `useReactTable` wiring), `AdminPaginationBar`, and `AdminCardList` (the mobile frame for skeleton / empty / items). `sort-adapter.ts` owns the one `column id → { asc, desc }` translation (`toSortingState` / `fromSortingState`), which the catalogue and orders columns each declare as a map. Panels keep their columns, filters, card bodies and skeleton shapes. The categories panel is deliberately still a client-sorted, unpaged table — it does not go through `useAdminListTable`, only through the card frame. **Resolved Sep 2026 (architecture review, candidate 3).**

### Checkout steps module — *seam*
`src/components/order/checkout-steps.tsx` + `CheckoutField.tsx`. The three checkout steps live outside the route, each taking the one thing it needs (`checkout`, the hook's state), and `CheckoutStep` owns the step partition the route used to restate as `currentStep === 1 | 2 | 3`; `CHECKOUT_STEP_COUNT` in `useCheckoutForm` owns the bounds. `fieldA11y` / `CheckoutError` / `CheckoutHint` own the per-field id ↔ error-id ↔ aria contract that nine fields each restated by hand. `app/order/page.tsx` is now the shell plus submit. **Resolved Sep 2026 (architecture review, candidate 4).**

### Database retry policy
`src/lib/prisma.ts`. The transient-connection retry policy (3 attempts, 1s/2s backoff, `isRetryableConnectionError` set) is one named function, `withDbRetry`, that both proxy branches compose — the model proxy and the top-level `$transaction`/`$queryRaw`/`$executeRaw` branch. It is exported so the policy is testable without a database. **Resolved Sep 2026 (architecture review, candidate 5)** — do not re-inline a retry loop around a Prisma call.

### Catalogue read module — *seam*
`src/lib/product-read.ts`. The SQL read surface for the catalogue: catalogue SSR (`listCatalogue`), category pages (`listByCategory`, plus the public view coercion `toProductView`/`toCatalogueProductView`), active-category options (`loadActiveCategories`), and gift-box lookup (`listGiftBoxes`). It imports the shared `SORT_OPTIONS` rather than declaring its own `DEFAULT_ORDER`; `CATEGORY_SORT_MAP` is now just the category page's allowed-key allow-list pointing at the shared table, re-exported from the [Sort contract module](#sort-contract-module--seam). **Resolved by the Sep 2026 review** — an ordering rule belongs in `SORT_OPTIONS` or it doesn't exist. Both new surfaces cache through the module-owned caches: `listCatalogue` keys `productsCache` by `host:list:categoryId` (no search — SSR search never reaches the fetch, so no key), and `loadActiveCategories` reads/writes the `categoriesCache` `active` key shared with the public `/api/categories` handler. The SSR catalogue page stopped hand-rolling cache get/set and bespoke `cat:`/`cats:` keys; it reads through these surfaces. **Resolved by the Sep 2026 review** — catalogue SSR reads go through one owned-cache surface; invalidation reaches the page, search stays out of cache keys. Two further surfaces belong here (Sep 2026 pass-3 review): `listProductsForQuery(hostname, query)` is the single `/api/products` list read — it owns the status gate (`active` → the in-memory index; `all`/`inactive` → Postgres through `productsCache`), the where-builder and the envelope, leaving the route to parse the URL and enforce the session; and `getProductDetail(id, hostname)` is the product-detail read — module-owned `unstable_cache` under the `product-detail` tag, with the active / soft-deleted / domain-visibility checks running **outside** the cache (one host's visibility verdict must never be served to another) and the returned view carrying the raw image pieces (`imageUrl` + `images`) — the primary pick is left to the display seam's `primaryImage()`, so JSON-LD, og/twitter, and the gallery all read the one picker's answer. (The precomputed `primaryImageUrl` shortcut was retired in the round-3 review — it duplicated the picker.) **Security rule:** `isActive=all|inactive` on `GET /api/products` requires an admin session and answers `private, no-store` — the gate lives at the route seam, so no branch can forget it. **Resolved by the Sep 2026 pass-3 review** — one list read, one detail read, no page-private Prisma cache, no anonymous enumeration of inactive products. **Read-through completed (Sep 2026 architecture review, candidate 3):** `listByCategory` now owns the `catPageCache` key (`host:slug:page:limit:sort`) and its hit/miss branch — the route is parse → call → envelope, and the SSR category page shares the same entries — and `listGiftBoxes` owns the `giftBoxCache` `all` key. A missing/inactive category is deliberately **not** cached, so a 404 cannot outlive its cause.

**Latest-per-category moved here (Oct 2026, architecture review candidate 5).** `listLatestPerCategory()` was the one catalogue SSR read living in the *cache* module, so the homepage kept its own query and projection while every other catalogue read went through this module. It sits here now against the module-owned `catLatestCache` (`catalogue-cache.ts` exports that cache and nothing else for this surface), and both callers -- `app/page.tsx` and `GET /api/categories/latest` -- go through it. The homepage also passes `undefined` rather than `[]` when the read throws, which is what makes the block's own client fetch a live recovery path instead of an unreachable branch.
### Order cache module — *seam*
`src/lib/order-cache.ts`. Owns the order-detail cache (`order`) and the tracking cache (`track`), plus `invalidateOrderCache(orderId?)`. Order-derived **stats are cleared here too** — on any order mutation (status change / tracking update), the dashboard cache must refresh. Its two read surfaces are `getOrderDetail(id)` (cache-first, Prisma fill on a miss, 30s TTL), used by the SSR confirmation page — which dropped its `revalidate = 30` build-time ISR (unreachable by any cache invalidation) for `force-dynamic` + this read surface — and `getTrackedOrders(orderId, phone)` (**added Sep 2026 architecture review, candidate 3**), which owns the tracking key, the hit/miss branch, the lookup's own 400 (no id *and* no phone), and the projection through `formatOrderResults`; `/api/track` only rate-limits, parses, and envelopes. **Resolved by the Sep 2026 review** — order reads go through the module's cache; no route/page reads an order straight from Prisma. (Round-6 review: this was true of the detail and tracking surfaces but **false of the admin list** — see below. The rule now holds for all three.)

**One audience rule for unauthenticated reads (Sep 2026, architecture review candidate 4).** "Look at an Order without a session" had two interfaces: the tracking seam demanded id + phone behind rate limiting, while `GET /api/orders/{id}` answered a bare UUID from the edge — a PII body in a shared CDN, keyed by nothing — and no in-app surface called it. `getOrderDetailForAudience(id, phone)` is now the **one** unauthenticated order read: it applies the tracking contract (id **and** the order's phone, validated by the shared `checkout-fields` rule), answers 404 — not 403 — for a phone mismatch so the endpoint can't be used to probe which ids exist, and the route answers `private, no-store` under the existing `track` rate-limit policy. Nothing in-app regresses: the confirmation page and the admin surfaces read `getOrderDetail` in-process. The rule to keep: **an unauthenticated Order read is a two-factor read; the audience decision lives in the Order cache module, never in the route.** The public-surface change (a new required `phone` query param) is recorded in the OpenAPI contract.

**The admin list read (round-6 review).** `src/lib/order-read.ts` is the module those two surfaces are built on, and it is the order-side sibling of `product-read.ts` — it holds `buildTrackCacheKey`, `queryOrdersByOrderId`, `queryOrdersByPhone`, `formatOrderResults`, and now `listOrdersForAdmin`. The admin orders list used to be the *one* order surface that reached past this module into Prisma: `GET /api/orders` ran `prisma.order.findMany` + `count` inline, which made the "no route reads an order straight from Prisma" claim above false, and the codebase over-trusted it. `listOrdersForAdmin` owns the where/status cast, the item include and the sequential (not `Promise.all`) pair of queries, so the route is parse → call → envelope like every other order adapter. `AdminOrderRow` deliberately keeps `adminNotes`: the admin list is authenticated, and the [Order view module](#order-view-module--seam)'s rule that status-history notes never enter a view exists because *the tracking surface* is unauthenticated, not because notes are secret. `ORDER_SORTS` stays in the route — it is the dashboard's own column order, not a shared catalogue contract, so it is not merged into `SORT_OPTIONS`.

### Stats cache module
`src/lib/stats-cache.ts`. The dashboard statistics cache **and its read surface** `getDashboardStats()` (cache-first, `computeDashboardStats` fill on a miss) — added Sep 2026 (architecture review, candidate 3) so `/api/stats` is envelope + error mapping only. Invalidation is owned by the Order cache module (stats derive from orders).

### Cache primitives
`src/lib/redis-cache.ts` (`createRedisCache(ttlMs, namespace)`) over `src/lib/cache.ts` (`createCache` in-memory fallback) and `src/lib/redis.ts`. The dual path is deliberate: Redis when `REDIS_URL` is set, in-memory fallback otherwise. Every cache exposes the `ttlMs` it was built with, so a caller can derive its edge header from the same number rather than restating seconds.

### Public cache-control module — *seam*
`src/lib/cache-control.ts`. The one home for the public edge TTLs: `PUBLIC_TTL` (per public read) and `publicCacheControl(ttlMs)`, which derives `s-maxage` from the TTL and doubles it for `stale-while-revalidate`. The owning cache modules build their cache *from* `PUBLIC_TTL` and export the matching header (`CATALOGUE_CACHE_CONTROL` in `catalogue-cache.ts`, `TRACK_CACHE_CONTROL` in `order-cache.ts`); routes and `openapi-spec.ts` import those instead of typing seconds. It is dependency-free on purpose, so `/api/docs` can import it without dragging Prisma or Redis in. **Resolved Sep 2026 (architecture review, candidate 3)** — this closes the "residual, named" note under the [Route guard module](#route-guard-module--seam): *each public read's CDN `s-maxage` restated the owning cache module's TTL — two homes for one number*. That sentence is retired; do not re-introduce a route-local `Cache-Control` for a public read.

### Cache-ownership rule
1. A route never creates a cache inline — it imports an owned cache from the module that owns the concept.
2. Invalidation clears what the owning module owns — never a hardcoded string list in a central file. **Extended (Sep 2026 architecture review, candidate 3):** a route never *keys* a cache either — the key, the hit/miss branch and the response's own validation live behind the owning module's read surface, so the adapter holds only parse/envelope/error mapping.
3. Mutating an Order (or its status) invalidates Order caches **and** stats; mutating any catalogue entity invalidates the whole Catalogue.

### Catalogue write module — *seam*
`src/lib/catalogue-write.ts`. The write-side sibling of `product-read.ts` — owns the mutation policy shared by two or more admin write routes so it has one home instead of N copies: `generateUniqueSlug(base, ignoreId?)` (first free slug, `-2`, `-3`, …; `ignoreId` lets an update keep its own slug) and `assertGiftBoxNotOnBox(categoryId)` (throws a `statusCode`-bearing Error that `withAdmin` maps to 400). Route-field builders, soft delete, and the 409-referenced-category block stay inline in their single calling route — dedupe only when a second caller appears.

### Pricing module — *seam*
`src/lib/pricing.ts`. One money computation shared by the checkout preview and the server finalize. Takes flat priced lines (`{ price, quantity, sku? }`) + `stateCode` → `{ subtotal, shippingCost, totalAmount }`. Owns the ₹599 free-shipping threshold, the TN/non-TN charges, and the `0000`-SKU test-product override; absorbs `calcShippingCost`. Two real callers justify the seam. Decided Sep 2026: subtotal **includes gift-box prices** so paid == stored going forward (historical orders keep their stored totals); money stays rupee floats — integer-paise arithmetic and the exact paid==stored comparison belong to the Order seam; display formatting lives beside it in `src/lib/format.ts`. Gift-box bundling rules stay with the Order intake, not Pricing. The shared **order projections** live here too: `orderLineViews` (flatten parent + gift-box rows in render order — admin modal, confirmation, PDF invoice) and `shippingProgress(subtotal)` (the ₹599 → `{ remaining, percent, unlocked }` — cart card, nudge popup, and `useShippingNudge` all render it; no surface recomputes the threshold). **Resolved Sep 2026 review** — do not re-implement threshold progress or totals formatting in a surface. **ADR-0003 (Sep 2026):** the packing label and Excel export are deliberate *operator artifacts* with their own line rows — the label's are editable at pack time and flat by design, the export dumps stored rows verbatim; `orderLineViews` stays the one projection for surfaces that *render order money to a reader*, and no `editable` variant was added.

### Order intake module — *seam*
`src/lib/order-intake.ts`. Owns the **Order lifecycle policy** behind one interface:

- **Placement:** `parseCreateOrderInput` (intent validation → `OrderError`/400) + `placeOrder` (gift-box bundling rules, stock checks, atomic decrements, ADR-0002 pricing basis, persistence with snapshots + status history, all inside a serializable transaction).
- **Fulfilment:** `parseUpdateOrderStatusInput` + `transitionOrderStatus` (versioned optimistic concurrency, tracking gate at `shipped`, `validateTransition` against the flow — no skips, no leaving `rejected`/`delivered` — and stock restore on `rejected`, atomic in a transaction) **and the tracking write** `parseUpdateTrackingInput` + `setTrackingId` (versioned, same 404/409 taxonomy; a tracking ID is editable in any status — pre-printed on packaging, corrected on delivered — the `shipped` gate lives on the status transition). The tracking route is a thin adapter over `setTrackingId`, exactly like the status route; both fulfilment input schemas are the shared `UpdateOrderStatusInputSchema`/`UpdateTrackingInputSchema` in `schemas.ts` (no module-local twin).
- **Invariants & taxonomy:** `assertPaidAmountMatchesTotal` (paid paise == stored total) and the `OrderError` class both paths map to HTTP. **The invariant cannot be skipped by omission (Oct 2026, architecture review candidate 3):** `placeOrder`'s `options.resolvedPaidPaise` is **required** and typed `number | null`, where `null` is a manual bank-transfer placement stating "no gateway charge". A gateway placement that forgot the field is a type error, and a slipped `undefined` now fails the amount comparison (400) instead of quietly skipping the check. `usePlaceOrder` moved out of `useAdminMutations` into `src/lib/hooks/usePlaceOrder.ts` — it is the app's one public mutation and an operator never places an order.

`POST /api/orders` and `PATCH /api/orders/[id]/status` are thin adapters: parse → module call → error mapping (plus gateway resolution / cache invalidation, which are adapter concerns). **Resolved by the Sep 2026 review (candidate 1); paid-amount invariant wired and fulfilment deepened the same month** — tests hit the module interface directly (`src/__tests__/lib/order-intake.test.ts`, `src/__tests__/lib/order-fulfilment.test.ts`); no HTTP harness.

### Order view module — *seam*
`src/lib/order-view.ts`. Owns the **read projection** of an Order — the one interface the confirmation page, the tracking results, the shared order-detail modal, and the PDF invoice consume. `toOrderView(order)` takes an order row with `items` + `statusHistory` and returns the `OrderView` (money as numbers, items carrying `parentOrderItemId` so `orderLineViews` nests gift boxes, `itemCount`, and the status history oldest-first). `orderTimeline(status, history?)` returns timeline entries from the **persisted** `OrderStatusHistory` when the surface carries it, falling back to the forward flow (`rejected` → one step) when it doesn't — so no surface re-derives the timeline from `ORDER_STATUS_FLOW`. **Resolved by the Sep 2026 review (candidate 1)** — before this, three surfaces projected the Order independently and disagreed: the tracking projection dropped `subtotal`/`shippingCost`/`parentOrderItemId`, so the shared modal rendered `₹NaN` and flattened gift boxes on the track surface, and the modal recomputed the timeline while the audit trail sat unused. Two rules survive: (1) no surface projects an Order row itself — read through `toOrderView`; (2) `OrderStatusHistory.notes` stay server-side and are never projected into a view (the tracking surface is unauthenticated). Tests hit the module interface (`src/__tests__/lib/order-view.test.ts`).

### API docs contract — *seam*
`src/lib/openapi-spec.ts` derives from `src/lib/api/schemas.ts` — the docs are **generated from the live contract, not typed beside it**. `openApi(schema)` (native `z.toJSONSchema(schema, { target: "openapi-3.0" })`, then Zod's `additionalProperties: false` dropped because Zod strips unknown keys rather than rejecting them) is the one Zod → OpenAPI step. Derived from it: the `GET /api/products` envelope, `GET /api/categories`, `GET /api/categories/latest`, `GET /api/category/{slug}/products`, both `GET /api/auth/me` responses, the `PATCH /api/orders/{id}/status` body, the `GET /api/track` response, and the `Product` component. Enum vocabularies are read from their source and never re-typed: `ORDER_STATUS_ENUM` ← `ORDER_STATUS_ALL`, `ROLE_ENUM` ← `SessionSchema.shape.role`, `BADGE_ENUM` ← the `ProductBadge` database enum. Request bodies that carry prose (create/update product, checkout) stay hand-written, and the `Order`/`OrderDetail` components stay hand-written because `OrderSchema` unions two endpoints' shapes. `src/__tests__/lib/openapi-contract.test.ts` pins documented shapes back to the schema tree. **Track shape derivation (round-3 review):** `TrackOrderResultSchema` = `OrderSchema.omit({ version: true }).extend({ itemCount: z.number().optional() })` — `itemCount` stays optional because the shared order-detail modal accepts `Partial<Order> & TrackOrderResult` and an admin Order row carries no count — and `/api/track` was the last hand-typed endpoint, now retired alongside the derived `Order`/`OrderDetail` siblings (its derived shape intentionally drops `format: uuid`/`date-time`, consistent with the others). **Resolved by the Sep 2026 review (candidate 5)** — do not hand-type a shape that has a Zod schema, and do not re-add a hand-copied enum.

### Route guard module — *seam*
`src/lib/route-guard.ts`. Owns **everything a route must do around its policy, for both audiences**: the CSRF origin check, the session policy (`withAdmin` requires an admin session and hands it to the handler; `withPublic` requires none), optional named rate limiting (`rateLimit: "order"` — the ceiling, its refusal copy and the key live in the rate-limiter module), optional JSON body parsing (400 on invalid JSON), the shared error taxonomy (`statusCode`-bearing domain errors like `OrderError`/`RazorpayGatewayError` keep their status; Prisma `P2002` → 409 with route-specific copy via `errorMessages`; `P2025` → 404; `P2034` (serialization conflict) → 409; anything else → 500 with the route's fallback), and the optional catalogue-refresh epilogue (`revalidateCatalogue: true` → `invalidateCatalogCaches` + the three public `revalidatePath` surfaces, only after a 2xx). Routes declare `withAdmin(handler, opts)` or `withPublic(handler, opts)`; the handler receives `{ request, params, body }` — plus `admin` when wrapped by `withAdmin` — and holds only the actual policy. **Resolved by the Sep 2026 pass-2 review (candidate A)** — migrated across products, categories, orders (GET/status/tracking), stats, and export. Do not re-suggest per-route guard consolidation; a new route of either audience uses the guard.

**Deepened Sep 2026 (architecture review, candidate 2) — the public routes are wrapped too.** Five hand-written prologues had drifted from the shared taxonomy (only `POST /api/orders` knew Prisma's `P2034`, so one serialization conflict answered 409 on placement and 500 on an admin fulfilment) and the 429 copy was written five times. **Named exception:** the two hybrid GETs — `/api/products` (the `isActive` status gate) and `/api/categories` (`includeInactive`) — branch audience inside one handler because Next allows one exported `GET` per route; they compose `requireAdmin()` and keep their own failure envelope. Do not re-suggest wrapping them, and do not re-inline a route's prologue. **Rate-limit rule (extends ADR-0001 rule 2):** a route never composes a rate-limit key either — `src/lib/rate-limiter.ts` owns the named policies (`RATE_LIMIT_POLICIES`), the client-IP extraction and the 429 envelope behind `guardRateLimit(policy, request)`. Tests: `src/__tests__/lib/route-guard.test.ts` and `rate-limiter.test.ts` hit the module interfaces directly. **Residual, named (resolved Sep 2026, architecture review candidate 3):** each public read's CDN `s-maxage` restated the owning cache module's TTL — two homes for one number. Now the [Public cache-control module](#public-cache-control-module--seam) owns it; the residual is closed.

### Product display module — *seam*
`src/lib/product-display.ts`. One home for the display transforms every customer and admin surface renders from: `stockHealth` (one low-stock threshold, `LOW_STOCK_MAX`), `primaryImage` (the **one picker**: primary gallery image → single image → the shared `IMAGE_UNAVAILABLE_PLACEHOLDER` — card/detail images, JSON-LD, and og/twitter all call it), and `productDisplayView` (price/compare/discount math + one badge-class map). The **load-failure half** lives in `src/components/ui/FallbackImage.tsx` — the one component every surface renders through: a broken src swaps to the same placeholder (tracked per-src, so a reused instance resets on src change) and an empty src fails upfront instead of throwing. No surface keeps its own `imgFailed` swap state or URL-validity gate. Created because the thresholds and pick had drifted across views (the low-stock cutoff was ≤3 on cards vs ≤5 on the detail page, and the detail page re-implemented the image pick). The detail read once surfaced a precomputed `primaryImageUrl`; the round-3 review deleted that shortcut so no surface can re-implement the pick. **Resolved Sep 2026 (round-3 review)** — one picker, one threshold, one discount formula. **Failure swap resolved Sep 2026 (round-4 review)** — one placeholder for null AND load failure. **One product shape resolved Sep 2026 (architecture review, candidate 4)** — the Zod contract is the only display product shape: `ProductCoreSchema` → `Product` / `CatalogueProduct`, plus the exported `ProductImage`. `ProductCard` takes `CatalogueProduct` and `useAddToCart` takes it too, so the `ProductData` / `ProductImageData` / `AddableProduct` twins are gone and a schema field can no longer stop reaching the card without a type error. The read module's `ProductDetailView` is the one deliberate narrowing (`imageUrl`/`description` non-null, `images` required — the detail read coerces them), and `ProductDetailsContent` consumes that type rather than declaring its own copy. One residual stays named: `src/lib/product-read.ts`'s exported `ProductView` / `CatalogueProductView` are structural copies of `Product` / `CatalogueProduct` (no external importers) — typing them as the schema types is a read-module change, not a display one.

### Gallery & Lightbox module — *seam*
`src/components/ui/ImageLightbox.tsx` (the deep core) + `src/components/ui/ProductImageGallery.tsx` (the composition). One home for **how a product image is viewed** — the Product display module owns *which* images (`primaryImage`, and `imageUrls(product)` for the full ordered list); this module owns *how they render*. The core `<ImageLightbox images initialIndex onClose zoom? onIndexChange?>` owns navigation (prev/next with wrap), the keyboard contract (ArrowLeft/ArrowRight/Escape **while open**, and never while an editable holds focus), the counter, the empty/degraded states, and every failure swap through `FallbackImage`. The old customer gallery's open-page arrow nav stays as that page's own local listener — a named exception the composition keeps, so the core's contract remains lightbox-only. Zoom (wheel + buttons + clamp + reset) is core behavior behind an opt-in `zoom` prop, not a surface-private extra. `<ProductImageGallery>` is a thin composition that owns the thumbnail strip and the main-image stage and opens the core; the admin catalogue lightbox and the product-form lightbox render the core directly (`imageUrls(product)` from the Product display module hands over the list — a viewer never re-picks which images exist), and overlay scaffold/focus behavior is the Modal module's concern, not this one's. Replaces three independent viewers that had already disagreed about failure handling — the detail gallery kept its own `failedImages` set, regressing the round-4 "no surface keeps its own swap state" rule on the biggest image surface. Tests hit the module interface (keyboard nav, wrap-around, zoom clamp, failure states) — `src/__tests__/components/ui/ImageLightbox.test.tsx`. **Resolved Sep 2026 (architecture review, candidate 1).**

### Cart projections module — *seam*
`src/lib/cart-projections.ts`. The **one home for what a cart becomes when it crosses a boundary**, and therefore the one home for the rule that decides which lines carry money. Three encoders, one private rule (`billableItems` — parents and their gift boxes, never the surprise gift):

- **`cartItemsToWire`** — the cookie boundary: cookie name/lifetime constants (`CART_COOKIE`, `CART_MAX_AGE`), the server-parsing wire schema `cartSchema` (RFC-4122 UUIDs, positive-int quantities, optional gift boxes), surprise gifts stripped and gift-box lines reduced to ids. Its input (`WireCartLine`) is deliberately **price-free**.
- **`cartPricedLines`** — the money boundary: flat `PricedLine[]` for the Pricing module's `computePricing`, each parent line first (carrying its `sku`, which the `0000` test-product shipping rule needs) then that parent's gift-box lines. It returns lines, never a sum — `computePricing` stays the one place money is computed, and `CartProvider` sums the projection for its own total.
- **`cartOrderItems`** — the intake boundary: the `POST /api/orders` payload rows (`id` keys, typed as `CreateOrderRequest["items"]`).

Both boundary sides import it — the server read (`cart-cookie.ts` parses `cartSchema`) and the client write (`CartProvider` serializes through `cartItemsToWire`) — so a boundary change is one edit, and cookie I/O stays on each side (the server side is `next/headers`-bound and must never be imported by the client). The two input shapes are deliberate: `WireCartLine` carries no prices because that boundary reads none, while `BillableCartLine` carries `price`/`sku` for the two money-bearing boundaries — one widened shape would make the wire contract appear to depend on fields it never uses. Tests hit the encoders directly (`src/__tests__/lib/cart-projections.test.ts`), including a cross-encoder test that the money and intake projections select the same parents. **Resolved Sep 2026 (round-3 review)** — the wire contract is no longer declared twice. **Deepened Sep 2026 (architecture review, candidate 2)** — the billable-lines rule had three homes (`CartProvider.computeItemsTotal`, the checkout page's `pricedLines`, `useCheckoutForm`'s `orderPayload`) and now has one, so the module is named for the concept instead of for one of its three boundaries. The two *count* surfaces deliberately stay out: `CartProvider.getCount` counts units and `OrderSummaryCard`'s display count counts lines — different quantities — so neither maps onto an encoder here; if a third count appears, that is the signal to deepen.

### Label draft module — *seam*
`src/components/admin/label-draft.ts`. Owns the **packing-label draft** — the editable state of a Packing label at pack time — as a pure state machine with no React: `draftFromOrder(order, now?)` (prefill + the ADR-0003 `productsFromOrder` projection + today's pack date behind an injectable `now`), `update(d, patch)` (one type-checked entry for every scalar field — not fourteen setters; `products` is deliberately absent), `selectCourier(d, option)` (owns the option↔custom wipe rule), `courierName(d)` (**derived**: `Other` → custom text, else the option — the select/custom/name trio can no longer desync), row ops `addRow` / `updateRow` / `removeRow` (the ≥1-row invariant is private; out-of-range indices are no-ops), `reset(order, now?)`, `clear(now?)`, and `displayPackDate`. `PrintShippingLabelModal` holds **one** `useState<LabelDraft>` and renders; init, reset and clear each have one home instead of three enumerations of the same 14 fields (the Fallow-flagged `resetToOrderData` divergence is gone), and the JSX only reads the draft and calls ops. **ADR-0003 respected:** the draft owns *edits* only — `ProductRow` stays the label's own flat shape, `productsFromOrder` keeps one home (its address moved, not its rule), and no editable variant enters `orderLineViews`. **Resolved Sep 2026 (architecture review, candidate 1)** — tests hit the module interface directly (`src/__tests__/components/admin/label-draft.test.ts`); `collectLabelCSS` and `ShippingLabel` are untouched, so their tests survive unchanged.

### Skeleton & route-state module — *seam*
`src/components/ui/SkeletonLoader.tsx` + `src/components/admin/AdminRouteState.tsx` + `app/styles/loading.css`. Owns **how a surface looks while it loads**. The markup side: the primitives (`SkeletonText`, `SkeletonBlock`), `ProductCardSkeleton`, and `CatalogueGridSkeleton` — the shared composition the catalogue and category route `loading.tsx` twins used to restate as 43-line clones (the raw copies also dropped the name/price line heights, so those lines rendered 0px tall; reuse fixes it). The style side: `loading.css` is the ONE stylesheet home for the skeleton vocabulary — the class family, `shimmer`, and `skeletonShimmer`, each keyframe declared **exactly once** (the Sep 2026 review found a shadowed *reversed* `shimmer` in `keyframes.css` and `skeletonShimmer` pasted twice inside `loading.css`; both deleted), with `accessibility.css` deliberately keeping shimmer outside its reduced-motion keep-alive list. Dead `.delay-*` stagger utilities deleted from `admin.css` and `loading.css` (zero references — inline `animationDelay` is the live mechanism). Admin route states: `AdminRouteState` ({ heading, code, title, body, extra?, actions }) owns the chrome that `app/admin/error.tsx` and `not-found.tsx` restate as 38-line twins — each route keeps only its copy; it is intentionally not `"use client"` so the server not-found renders it directly. Route `loading.tsx` files compose the module instead of hand-rolling raw divs; the spinner-based root/docs loading files are deliberately untouched. **Panel-local skeletons stay local** — `order-card-skeleton`, `product-table-skeleton`, `categoryCardSkeleton()`, `chart-skeleton` keep their homes (dedupe only when a second caller appears). Tests: `src/__tests__/lib/skeleton-css.test.ts` pins the stylesheet contract (one shimmer, one skeletonShimmer, zero `.delay-*`); the existing `.skeleton-text` / `.product-card.chart-skeleton` assertions (AdminOrdersPanel, AdminDataTable, catalogue-pagination) survive unchanged. **Resolved Sep 2026 (architecture review 2, candidate 3).**

### Checkout payment seam
`src/lib/hooks/useCheckoutPayment.ts`. The Razorpay browser capture as a testable seam: create the gateway order → load the script → open Standard Checkout → verify the signature → place the order through the caller's mutation, resolving a typed `RazorpayOutcome` (`ok` / `cancelled` / `failed` / `error`). The page keeps validation, toasts, and navigation; the sequence was previously ~90 inline lines in `app/order/page.tsx` with no seam to test through. `getErrorMessage` (shared page/hook error wording) lives in `src/lib/api/client.ts`. Tests hit the hook interface with a fake Razorpay constructor (`src/__tests__/lib/hooks/useCheckoutPayment.test.ts`). **Resolved Sep 2026 (round-3 review).**

### Add-to-cart flow module — *seam*
`src/lib/hooks/useAddToCart.ts`. The **whole "add this product" lifecycle**, not just the add: an eligible product (`allowGiftBoxBundling`, and not itself a Gift Box) opens the gift-box modal instead of adding, and the modal's confirm / skip / close resolve back into the same cart write. The interface is two things — `handleAdd` for a product card's Add button, and `giftBox`, the ready-made `GiftBoxModal` props bundle a page renders as `{giftBox && <GiftBoxModal {...giftBox} />}` (or `null`). Both catalogue and category pages consume exactly that and keep no modal state; the flow's product mapping, its `as unknown as T` re-shape (the modal hands back a slim product, so stock is forced to 1), and the empty-list-means-undefined rule are private. Two facts earn the seam: the Cart module returns the authoritative post-add `newTotal` (the stale-read ₹0 nudge bug is structurally impossible through this call), and the old `open` flag was vestigial — the modal only ever rendered when a product was set, so the bundle's `open` is always true and the state is gone. **Resolved Sep 2026 (round-5 review, candidate 1)** — the two page copies (~45 lines each, line-for-line twins) are deleted; a new surface renders the bundle and nothing else. Tests hit the hook through the pages' behaviour (`GiftBoxModal.test.tsx`, `catalogue-pagination.test.tsx`) plus `CartProvider.test.tsx` for the cart write.

### Modal module — *seam*
`src/components/ui/Modal.tsx`. One home for the dialog scaffold: overlay, focus trap, Escape policy, body scroll lock, and the `role="dialog"` / `aria-modal` / `aria-labelledby` / `aria-describedby` wiring. The interface is one component — `<Modal open onClose labelledBy? label? describedBy? closeOnEscape? closeOnOverlayClick? overlayClassName contentClassName>` — and a modal supplies only its content and its close policy. `overlayClassName` / `contentClassName` exist because each surface has its own skin (`.modal-overlay` + `.modal-content`, the shipping-nudge sheet, the gift-popup card, the print-label box); owning the scaffold is not owning the CSS.

It replaced four Escape mechanisms (overlay `onKeyDown`, a `document` listener, a `window` listener, and a parent that suppressed Escape for a nested child), two scroll-lock styles (one restoring `""` over whatever was there), and two modals with no focus trap at all. Three rules survive:

1. **Nesting is a stack.** Only the top-most open `Modal` reacts to Escape, so a child never needs its parent to stand down — `OrderDetailModal` dropped its `!showPrintModal` guard. A child that must not be dismissed by Escape passes `closeOnEscape={false}` and still shields its parent (the shipping-label editor does exactly this: an operator shouldn't lose a half-typed AWB to a stray key).
2. **The scroll lock is a counter and restores the prior value**, so nesting can't unlock the page early and a page that arrived with `overflow: auto` gets it back.
3. **`ImageLightbox` is a named exception** — an image viewer, not a dialog: it keeps its own `window` keydown (arrows, plus the never-steal-from-an-editable guard) and has no focus trap. Its overlay semantics are not a second scaffold to copy.

**Resolved Sep 2026 (architecture review, candidate 2).** Tests hit the module interface (`src/__tests__/components/ui/Modal.test.tsx`) — Escape policy, the nesting stack, backdrop policy, and the scroll-lock restore.

### Image-set module — *seam*
`src/lib/image-set.ts`. Owns the product-gallery invariant **exactly one primary, contiguous `displayOrder` from 0**: `normalizeImageSet` (the stored form — first flagged image wins, or the first image when nothing is flagged; blank and duplicate URLs dropped) plus the ops the admin form is written in — `addImage`, `removeImage`, `setPrimary`, `moveImage`, `editImage`. Pure and framework-free, so the form and both write routes normalize identically. The rule was restated in four untested form handlers and only approximated in the routes, where `isPrimary ?? idx === 0` was **dead code** (Zod defaults the flag to `false`) and a gallery could be stored with no primary at all. Reads stay as they are: `primaryImage` in the [Product display module](#product-display-module--seam) is still the one picker and still tolerates drift on legacy rows.

**Resolved Sep 2026 (architecture review, candidate 5).** Tests hit the module interface (`src/__tests__/lib/image-set.test.ts`) and assert the invariant after every op, rather than restating the expected array per handler.

### Gift-box rule module — *seam*
`src/lib/gift-box.ts`. The **one** identity predicate for the Gift Box category and the one eligibility answer: `GIFT_BOX_CATEGORY_SLUG` (`"box"`), `GIFT_BOX_CATEGORY_WHERE` (the Prisma `where` fragment), `isGiftBoxCategory(category)`, and `canBundleGiftBoxes(product)` (opt-in **and** not itself a gift box). Dependency-free, so the client reads the same answer the server does.

It exists because the identity had two vocabularies: `slug === "box"` on the server (Order intake ×2, the write guard, the gift-box list, the admin form) and `name !== "Gift Boxes"` on the storefront (the detail button, add-to-cart). The client never even received the slug — `ProductSchema` / `CatalogueProductSchema` carried `category: { name }` and nothing else — so a rename, or an admin re-create (slug = `slugify("Gift Boxes")` = `gift-boxes`), split the storefront's offer from checkout's rules. The slug now travels with the name in both schemas and both product reads, the second vocabulary is **deleted**, and all seven sites import the predicate. **Resolved Sep 2026 (architecture review 2, candidate 2).** Two rules to keep: a category's **identity is its slug, its name is a label**; and the eligibility answer is computed once, never re-derived per surface. The placement rules themselves stay with the [Order intake module](#order-intake-module--seam).

### Gift-box selection module — *seam*
`src/components/pages/gift-box-picker.ts`. The **one home for the Gift Box picker's selection state**: the `GiftBox` / `SelectedGiftBox` shapes, one read of `/api/gift-boxes` (`useGiftBoxes(active)` — the modal defers it until it opens, the selector reads on mount), and the cap rule (`toggleBox` / `stepBox` / `canAddBoxes`, with `capBoxes` private). `GiftBoxModal` and `GiftBoxSelector` keep their own chrome and JSX only. The two surfaces used to declare the same two shapes and hand-roll the same unvalidated fetch, and **their cap rules had already diverged**: the selector caps box units at the parent quantity, the modal does not cap (pinned by `GiftBoxModal.test.tsx`, which asserts quantity > 1). The cap is now a **stated input per surface** (`BOX_CAP = Infinity` in the modal, `parentQuantity` in the selector) rather than an omission in one copy, so the two can differ on purpose and not by accident. **Resolved Oct 2026 (architecture review, candidate 1).** Tests hit the module interface (`src/__tests__/components/pages/gift-box-picker.test.ts`).

### Panel view-model actions are derived, not restated
The three panel view-models (`useAdminOrdersPanel`, `useAdminCataloguePanel`, `useAdminCategoriesPanel`) expose a typed `{ data, loading, actions }` view-model. Their action interfaces are **derived from the module behind them** — `Pick<ReturnType<typeof useAdminOrdersController>, …>` for fulfilment, and `CatalogueCrud["toggleForm"]` / `CategoriesCrud["save"]` indexed-access types over `useAdminCrud`'s own return — so a renamed or dropped source action is a type error at the view-model instead of a panel calling `undefined`. They previously re-declared every signature key by key, which made each one a pure rename band with no test to catch drift. **Resolved Oct 2026 (architecture review, candidate 4)** — do not re-declare a view-model's action signatures by hand. `useAdminOrdersPanel` now has the interface test the other two still lack (`src/__tests__/components/admin/useAdminOrdersPanel.test.tsx`).

### Catalogue listing module — *seam*
`src/components/pages/useCatalogueListing.ts`. Owns the listing **state** of `/catalogue` and `/category/[slug]`: the responsive page size, the projection of the React Query result onto what the grid needs, and the failure classification (`filterLoading` for a changed key, `filterError` + retry once retries finish), plus `ssrPageSlice` and the page-change handler (set page, scroll to top).

The two surfaces each kept a ~90-line copy of that state machine, and they had already diverged: **the category page had no failure branch at all**, so a failed sort fetch silently served the previous page's products. Each page now keeps only what is its own — the hero, its toolbar (search / category filter / sort), and the page number it must feed its own read — and the shared failure branch is what the category page gained. Tests hit the module interface (`src/__tests__/components/pages/useCatalogueListing.test.tsx`).

**The page size is one number**, `CATALOGUE_PAGE_SIZE` in `constants.ts`: it sizes the SSR payload (`listCatalogue`'s `take`), seeds the client query's default limit, and the client re-slices it to the responsive size for the first paint. It was restated in three places, and a mismatch meant a first paint wider than the layout. **Resolved Sep 2026 (architecture review 2, candidate 1).** No conflict with the [Sort contract module](#sort-contract-module--seam): this owns listing *state*, that owns the sort *vocabulary*.

**The seed is the query's own answer (Oct 2026, architecture review candidate 2).** `listingSeed(seed, page, pageSize, extra)` builds the response envelope React Query adopts, and the two query hooks (`useCatalogueProducts`, `useCategoryProducts`) call it themselves next to the `page === 1` rule that decides when the seed applies — so a page passes `{ products, total }` and nothing else. Previously both pages hand-built the same envelope, `as`-cast their SSR rows to the query's wider row shape, and re-inlined the page count the module already owned. **`pageSize` is now an argument**, not a second `useResponsivePageSize()` call inside the hook: each page subscribes to the media query once, and the seed and the query can never be sized differently. The one remaining cast is the narrow grid row meeting the endpoint's wider `Product` — that is the four-product-shapes question, not this seam.



Terms from the codebase-design vocabulary, used exactly in architecture discussion:

- **Module** — a unit with an interface and an implementation. A **deep** module hides big complexity behind a small interface; a **shallow** module has interface ≈ implementation.
- **Interface** — what callers must know to use the module. **The interface is the test surface** — tests should exercise the interface, not the HTTP harness.
- **Seam** — a place where behavior can be swapped or intercepted; the boundary a deepening refactor targets.
- **Adapter** — a thin layer translating between the module interface and the outside world (e.g. HTTP handlers, a payment gateway client).
- **Leverage** — how much work a small amount of interface buys; deep modules are high-leverage.
- **Locality** — related things living together; the opposite of "bounce across eight files to understand one concept."
- **Deletion test** — would deleting this module *concentrate* complexity (deep, keep it) or just *move* it (shallow, merge it)? "Yes, concentrates" is the signal for a deepening opportunity.

Findings from the Aug 2026 architecture review, not yet addressed:

- **Order module** (candidate 1, *Strong*) — placement / fulfilment / payment logic lives inline in HTTP handlers; inventory knowledge is split; the payment flow lacks an amount-integrity invariant. **Placement resolved (Sep 2026):** deepened into the [Order intake module](#order-intake-module--seam) (`placeOrder` + `OrderError` + parse + paid-amount assertion). **Paid-amount invariant wired (Sep 2026):** razorpay placements verify the charged amount against the gateway server-side and the intake asserts paid == stored before persisting. **Fulfilment resolved (Sep 2026):** status transitions deepened into the same module (`transitionOrderStatus` + `validateTransition` + `parseUpdateOrderStatusInput`); `PATCH /api/orders/[id]/status` is a thin adapter. **No open remainder** for this candidate.
- **Pricing policy** (candidate 2, *Strong*) — shipping + total computed twice (checkout preview vs server finalize). **Decisions made (Sep 2026):** deepen into `src/lib/pricing.ts`; subtotal includes gift-box prices (paid == stored, forward); rupee floats; separate `src/lib/format.ts`. **Implemented:** `computePricing` in `src/lib/pricing.ts` is the single money computation and both callers consume it — the checkout preview (`app/order/page.tsx`) and the server finalize (the Order intake's `placeOrder`); ADR-0002 records the basis.
