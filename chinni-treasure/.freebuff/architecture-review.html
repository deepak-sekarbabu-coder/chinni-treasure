Deepening Opportunities

Turning shallow modules into
deep ones that carry the complexity.

Five friction points surfaced while walking the storefront, the admin surface, and the order lifecycle. Each is a shallow module — an interface nearly as complex as its implementation, or a concept scattered across files so that understanding it requires bouncing between many small pieces. The proposed changes deepen them: fewer, richer modules whose interfaces hide real work, so the codebase becomes easier to test and easier for AI (and humans) to navigate.

Candidate 01 Strong

The admin route guard: compose the security posture once

Files

app/api/auth/login/route.ts app/api/products/route.ts app/api/products/[id]/route.ts app/api/categories/route.ts app/api/categories/[id]/route.ts app/api/orders/route.ts app/api/orders/[id]/status/route.ts app/api/orders/[id]/tracking/route.ts app/api/create-order/route.ts app/api/verify-payment/route.ts

Shared primitives that already exist: src/lib/csrf.ts src/lib/rate-limiter.ts src/lib/auth.ts

Problem

Every mutating route begins with the same ~12-line sequence: validateCsrfOrigin, then checkAuth, then a try/catch wrapping body parse + Zod safeParse + Prisma error mapping. Fallow counts this as two clone groups spanning 9 files / 175 lines. The interface — "three helper calls, remember to wrap in try/catch, remember the 400/401/409/500 mappings" — is nearly as complex as the work itself. A route author can forget the rate-limit, return the wrong status for a P2025, or skip the CSRF check entirely. The deletion test says: delete the guard in any one route and nothing concentrates — the knowledge simply evaporates, because it was never owned by a module.

Solution

A deep request-guard module: one requireAdmin(request, opts) that composes CSRF + JWT + optional rate-limit and returns { admin } | NextResponse, plus a parseBody(schema) and a shared Prisma error → response mapper. Each route collapses to: guard → parse → do → respond. The security posture of the entire admin surface lives in one file you can read top-to-bottom.

Before — 9 shallow routes, each re-implementing the guard
products/route csrf auth try/parse
products/[id] csrf auth try/parse
categories/route csrf auth try/parse
categories/[id] csrf auth try/parse
orders/route csrf auth try/parse
orders/status csrf auth try/parse
orders/tracking csrf auth try/parse
create-order csrf rate try/parse
verify-payment csrf rate try/parse
duplicated guard lines175
After — one deep guard module, routes become thin
requireAdmin() parseBody(schema) prismaError()
products/route requireAdmin → parse → do
categories/[id] requireAdmin → parse → do
orders/status requireAdmin → parse → do
create-order requireAdmin → parse → do
…plus 5 more one-liner routes
guard lines owned by one module~60 once

Benefits — locality, leverage, tests

  • Locality. CSRF ordering, auth, rate-limit, and error mapping sit together. A future "every mutation needs an audit log" change lands in exactly one file.
  • Leverage. The interface requireAdmin(request) hides 5 decisions. Adding admin endpoint #10 is 15 lines, not 15 lines of judgment calls.
  • Tests. The interface is the test surface: one suite can assert "403 without origin, 401 without session, 429 after N attempts" instead of nine partial re-tests.
Candidate 02 Strong

The product listing module: one deep listing, two thin pages

Files

src/components/pages/catalogue-content.tsx src/components/pages/category-content.tsx src/components/ui/ProductCard.tsx src/lib/hooks/useAdminData.ts src/lib/hooks/useShippingNudge.ts

Problem

catalogue-content.tsx and category-content.tsx are siblings that share ~121 lines across three clone groups: the same search box, category filter, skeleton grid, image-settling effect, page-transition dimmer, pagination bar, and add-to-cart + shipping-nudge wiring — differing only in the fetch hook and a few labels. Understanding "how does a listing work?" requires diffing two 250-line files. The interfaces are shallow: their props differ from each other more than their behaviour does.

Solution

One deep ProductListing module. Its interface is a small query config — the fetch function, initial data, and which affordances to show — instead of a bespoke hook per page. CataloguePage and CategoryPage become thin declarative wrappers that hand it a config. The third listing surface (a future "search results" or "sale" page) becomes a config, not a fourth copy.

✓ add-to-cart nudge
121 duplicated lines · two files that must be kept in lockstep

Benefits — locality, leverage, tests

  • Locality. The image-settling + page-transition dance, the one part of the UI that has real timing logic, exists in exactly one place.
  • Leverage. A third listing surface is a config object, not another copy to keep honest. The seam is the config, and the config is small.
  • Tests. The existing pagination test suite gains a single, comprehensive surface; category and catalogue behaviour can no longer drift apart.
Candidate 03 Worth exploring

The free-shipping incentive: a domain module two presenters share

Files

src/components/order/OrderSummaryCard.tsx src/components/ui/ShippingNudgePopup.tsx src/lib/hooks/useShippingNudge.ts src/lib/constants.ts

Problem

Fallow flags a 248-line clone between these two files — and the "how close to free shipping" progress math, the formatRupees Intl formatting, and the threshold constant are implemented twice with slightly different copy. The free-shipping incentive is a real domain concept (threshold, remaining amount, progress percent, unlocked state) but it has no home: it leaks out of the presenters instead of being a module. Each presenter's interface is shallow — it re-derives the same numbers its sibling does.

Solution

A deep free-shipping incentive module: one useFreeShippingIncentive(cartTotal) returning { remaining, percent, unlocked, messages }, plus a shared formatRupees in one place. OrderSummaryCard and ShippingNudgePopup become thin presenters of the same state — and any future surface (cart dropdown, checkout sticky bar) gets the incentive for free.

Before — one concept, two implementations
OrderSummaryCard
formatRupees() · progress% · remaining · "Add ₹X more"
ShippingNudgePopup
formatRupees() · progress% · shippingLeft · "Add ₹X more"
248 duplicated lines — the copy drifts first, then the math
After — one domain module, two presenters
useFreeShippingIncentive(total)
remaining · percent · unlocked · formatRupees · copy — owned once
OrderSummaryCard
NudgePopup

Benefits — locality, leverage, tests

  • Locality. Threshold, rounding, and message copy are domain decisions that belong together. Change "free over ₹999" in one place.
  • Leverage. The cart dropdown, sticky checkout bar, and order confirmation all want this state eventually — the module is ready for them.
  • Tests. The incentive math (rounding edge cases, exactly-at-threshold, zero total) becomes unit-testable without rendering any component.
Candidate 04 Worth exploring

Checkout orchestration: pull the payment flow out of the page

Files

app/order/page.tsx src/lib/hooks/useAdminMutations.ts src/lib/razorpay.ts app/api/create-order/route.ts app/api/verify-payment/route.ts src/lib/api/index.ts

Problem

app/order/page.tsx is 668 lines and carries nine functions above the complexity threshold. It mixes three distinct jobs: form orchestration (three steps of validation rules), money math (shipping cost, grand total, test-product bypass), and the Razorpay lifecycle (script load → create order → handler → verify → place order → navigate). The payment sequence especially is a deep, stateful protocol buried inside JSX handlers — its failure modes (dismiss, payment.failed, verification failure) are only reachable through a browser.

Solution

Extract the money math into a pure checkout totals module (computeShipping(total, state, isTestProduct)) and the payment protocol into a useRazorpayCheckout hook that owns script → order → handler → verify → placeOrder and surfaces the outcome. The page keeps only presenters and step navigation. The interface is the test surface: the whole payment protocol becomes mockable.

Before — the page is the whole system
app/order/page.tsx · 668 LOC
validation rules · step nav · shipping math · grand total · Razorpay script · order create · payment handler · verify · placeOrder · toast · navigate
browser required to exercise any of it; bugs hide in the wiring
After — three deep modules, a thin page
useCheckoutForm — rules + step state
computeTotals() — pure money math
useRazorpayCheckout — payment protocol
page — presenters + nav only

Benefits — locality, leverage, tests

  • Locality. The payment protocol's states and failure modes sit in one module you can read top-to-bottom, not scattered across a 668-line render.
  • Leverage. A future "pay later / COD" checkout reuses the form and totals modules and swaps only the payment adapter.
  • Tests. The verify→placeOrder→navigate sequence, and the totals math, become testable without a browser or a real Razorpay order.
Candidate 05 Speculative

The shipping label: separate generation from presentation

Files

src/components/admin/PrintShippingLabelModal.tsx

Problem

PrintShippingLabelModal is a single 728-line function (16 hooks) that couples two genuinely different concerns: generating the label (jsPDF layout, barcode, address blocks, courier formatting) and presenting it (modal open/close, size presets, print wiring). The generation logic — the part a courier actually depends on — is untestable through this interface: you must mount the modal to touch it. This one is marked speculative because the payoff is real but the modal is also just large; the deepening is low-risk and high-value.

Solution

A pure generateShippingLabel(order) module returning { svg, pdfBytes, pageCount } — deterministic, dependency-injectable (pass a jsPDF instance for tests). The modal becomes a thin presenter that calls it. Label layout rules become a testable, reusable domain artifact.

Before — 728 LOC, generation welded to the modal
PrintShippingLabelModal: 16 hooks · jsPDF layout · barcode · size presets · print · modal
→ to test the label, you must render the modal
After — a pure generator behind a seam
generateShippingLabel(order) → { svg, pdf, pages }
modal → present + print
→ label layout unit-tested headlessly

Benefits — locality, leverage, tests

  • Locality. Courier-facing layout rules (barcode placement, address block, margins) become a single source of truth instead of lines inside a component.
  • Leverage. The generator could serve an API endpoint or a batch print flow later without dragging the modal along.
  • Tests. PDF/barcode output becomes assertable in CI — the label is the one artefact whose exact bytes matter to the business.

Top Recommendation

Start with Candidate 01 — the admin route guard

It is the highest-leverage and lowest-risk deepening on the list:

  • Largest duplication, smallest surface. It removes the two biggest fallow clone groups (175 lines across 9 files) while touching only additive helpers — every route keeps its behaviour.
  • The seam already exists. validateCsrfOrigin, checkAuth, checkRateLimit are primitives waiting for composition — this is deepening, not new design.
  • Security posture in one file. The guard is exactly the kind of module where "the interface is the test surface": a 403/401/429 suite covers the whole admin surface.
  • Unblocks everything else. Ordering/verification routes (Candidate 04) and every future admin endpoint get cleaner once the guard is one call.

No domain glossary (CONTEXT.md) or ADRs exist yet — if any of these deepenings are later rejected for a load-bearing reason, that's the moment to record an ADR so future reviews don't re-suggest them.
