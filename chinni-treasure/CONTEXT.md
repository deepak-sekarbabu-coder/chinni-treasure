# Chinni Treasure — Domain Glossary (CONTEXT.md)

Living vocabulary for architecture reviews and agents working in this codebase.
Architecture terms follow the codebase-design vocabulary (see [Design vocabulary](#design-vocabulary)).
Terms marked **seam** are names for good module boundaries — use them when talking about deepening opportunities.

## Domain concepts

| Term | Meaning | Where it lives |
|---|---|---|
| **Product** | The sellable unit. Has `sku`, `price`, `compareAtPrice` (MRP for strikethrough display), `stockQuantity`, `badge`, `visibleHostnames` (multi-domain filter), soft-delete (`deletedAt`), and multiple `ProductImage`s (one primary). | `prisma/schema.prisma` |
| **Category** | Product grouping with `slug`, `displayOrder`, `isActive`. Deleting is blocked while non-deleted products reference it (409). | `prisma/schema.prisma`, `app/api/categories/*` |
| **Catalogue** | The customer-facing listing surface: product listings, category pages, "latest per category", and recent products. Treated as **one concept** for caching — see [Catalogue cache module](#architecture-modules). | `app/api/products/*`, `app/api/categories/*`, `app/api/category/[slug]/products` |
| **Cart** | Guest cart: React Context + `localStorage`, synced to a server-side cookie for SSR. The mutators are **deep**: `addItem` returns `{ result, newTotal }` where `newTotal` is the authoritative post-add total computed from the committed state — callers never re-derive "total after this add" from a stale `getTotal()` (that stale read was the ₹0 shipping-nudge popup bug, fixed Sep 2026). The Cart module is the only place that knows its own asynchrony. The cookie wire shape (what crosses the client/server boundary) is **one projection** owned by `src/lib/cart-wire.ts` — schema, serializer, cookie name/lifetime — imported by both the server read side (`cart-cookie.ts`) and the client write side, so a wire change is one edit, never two coordinated ones. | `src/components/cart/CartProvider.tsx`, `src/lib/cart-cookie.ts` |
| **Checkout** | The multi-step order page (details → delivery → payment & review). Computes a client-side preview of totals. The Razorpay capture sequence is a **seam**: `useCheckoutPayment` owns create-order → open Standard Checkout → verify signature → place (through the page's mutation) and resolves a typed outcome — the page keeps validation, toasts, and navigation. | `app/order/page.tsx`, `src/lib/hooks/useCheckoutPayment.ts` |
| **Pricing** | The money module: subtotal (parent lines **plus** gift-box lines), shipping (₹599 free threshold; ₹150 TN / ₹200 elsewhere; `0000`-SKU test product ships free), and total. Carries rupee floats; the exact paid==stored invariant is owned by the Order seam. Decided Sep 2026: subtotal includes gift-box prices — paid == stored going forward. | `src/lib/pricing.ts` |
| **Order** | The aggregate: `orderNumber`, customer + address, `status`, `version` (optimistic concurrency), `subtotal`/`shippingCost`/`totalAmount`, `transactionId`, `trackingId`, `items`, `statusHistory`. Surfaces render the **Order view** projection, never the row — see [Order view module](#order-view-module--seam). | `prisma/schema.prisma` |
| **OrderItem** | Price/name snapshot of a product at purchase time; `productId` is nullable (SetNull when the product is deleted). | `prisma/schema.prisma` |
| **Fulfilment** | The status flow: `pending → approved → packaging → shipped → delivered`, with `rejected` (restores stock). Tracking ID required at `shipped`; transitions are versioned and **validated against the flow** (no skips, no leaving terminal states). Owned by the Order intake module's fulfilment half. | `src/lib/order-intake.ts` (`transitionOrderStatus`), `src/lib/constants.ts` (`ORDER_STATUS_FLOW`) |
| **Payment** | The Razorpay gateway flow, deepened into one module (`src/lib/razorpay-server.ts`): `createGatewayOrder` (order creation for Standard Checkout — rupees in, paise conversion and the minimum-amount policy inside), `verifyCheckoutSignature` (HMAC-SHA256 in constant time), and `acceptPlacementPayment` (the paid==stored prologue: authoritative snapshot from `payments.fetch` that must belong to the given order and be `captured`/`authorized`). Routes are thin adapters — parse → module call → error mapping via `RazorpayGatewayError`; `transactionId` is recorded on the Order and `placeOrder` asserts paid paise == stored total (ADR-0002) before persisting; manual bank-transfer placements skip the gateway check. | `src/lib/razorpay-server.ts`, `src/lib/order-intake.ts` |
| **Inventory** | `stockQuantity` on Product. Deducted atomically at order placement (serializable transaction), restored on rejection. | `src/lib/order-intake.ts` (`placeOrder`) |
| **Admin** | The dashboard surface: JWT session in an HttpOnly cookie (`proxy.ts` guards `/admin/*`), roles `admin` / `super_admin`, stats + charts, catalogue/category/order CRUD. | `app/admin/*`, `src/lib/hooks/useAdmin*Controller.ts` |

## Architecture modules

These are **deep modules** — small interfaces, big hidden implementations — that own a concept. Future reviews should deepen around these seams, not re-litigate them.

### Catalogue cache module — *seam*
`src/lib/catalogue-cache.ts`. Owns **all six catalogue caches** (`products`, `catindex`, `categories`, `catlatest`, `catpage`, `recent`) and exports `invalidateCatalogCaches()`, which clears exactly what the module owns (the namespace in Redis via SCAN+DEL **plus** the local in-memory fallback). Routes import their cache from this module; they never call `createRedisCache` themselves. **Resolved by the Aug 2026 architecture review** — do not re-suggest a hardcoded namespace list. The `catindex` cache holds the full active-product list per hostname so public catalogue searches filter in memory instead of querying Postgres per request. The index query surface (`queryCatalogueIndex`, filter/sort/page over `catindex`) lives in this module too, so the route only parses, calls, and envelopes. `SORT_OPTIONS` — the **one catalogue order contract** — lives here too: every entry is a complete orderBy (in-stock first, then the chosen field, then id desc), consumed verbatim by the `/api/products` status branch (`listProductsForQuery` in `product-read.ts`), the category pages, and the in-memory `catIndex` comparator (which walks the same arrays). Changing a sort rule means editing `SORT_OPTIONS`; no route re-declares an order. **Resolved by the Sep 2026 review** — do not re-add per-route orderBy mirrors.

### Catalogue read module — *seam*
`src/lib/product-read.ts`. The SQL read surface for the catalogue: catalogue SSR (`listCatalogue`), category pages (`listByCategory`, plus the public view coercion `toProductView`/`toCatalogueProductView`), active-category options (`loadActiveCategories`), and gift-box lookup (`listGiftBoxes`). It imports the shared `SORT_OPTIONS` rather than declaring its own `DEFAULT_ORDER`; `CATEGORY_SORT_MAP` is now just the category page's allowed-key allow-list pointing at the shared table. **Resolved by the Sep 2026 review** — an ordering rule belongs in `SORT_OPTIONS` or it doesn't exist. Both new surfaces cache through the module-owned caches: `listCatalogue` keys `productsCache` by `host:list:categoryId` (no search — SSR search never reaches the fetch, so no key), and `loadActiveCategories` reads/writes the `categoriesCache` `active` key shared with the public `/api/categories` handler. The SSR catalogue page stopped hand-rolling cache get/set and bespoke `cat:`/`cats:` keys; it reads through these surfaces. **Resolved by the Sep 2026 review** — catalogue SSR reads go through one owned-cache surface; invalidation reaches the page, search stays out of cache keys. Two further surfaces belong here (Sep 2026 pass-3 review): `listProductsForQuery(hostname, query)` is the single `/api/products` list read — it owns the status gate (`active` → the in-memory index; `all`/`inactive` → Postgres through `productsCache`), the where-builder and the envelope, leaving the route to parse the URL and enforce the session; and `getProductDetail(id, hostname)` is the product-detail read — module-owned `unstable_cache` under the `product-detail` tag, with the active / soft-deleted / domain-visibility checks running **outside** the cache (one host's visibility verdict must never be served to another) and the returned view carrying the raw image pieces (`imageUrl` + `images`) — the primary pick is left to the display seam's `primaryImage()`, so JSON-LD, og/twitter, and the gallery all read the one picker's answer. (The precomputed `primaryImageUrl` shortcut was retired in the round-3 review — it duplicated the picker.) **Security rule:** `isActive=all|inactive` on `GET /api/products` requires an admin session and answers `private, no-store` — the gate lives at the route seam, so no branch can forget it. **Resolved by the Sep 2026 pass-3 review** — one list read, one detail read, no page-private Prisma cache, no anonymous enumeration of inactive products.

### Order cache module — *seam*
`src/lib/order-cache.ts`. Owns the order-detail cache (`order`) and the tracking cache (`track`), plus `invalidateOrderCache(orderId?)`. Order-derived **stats are cleared here too** — on any order mutation (status change / tracking update), the dashboard cache must refresh. Its single order-detail read surface is `getOrderDetail(id)` (cache-first, Prisma fill on a miss, 30s TTL), used by the `/api/orders/[id]` route and the SSR confirmation page — which dropped its `revalidate = 30` build-time ISR (unreachable by any cache invalidation) for `force-dynamic` + this read surface. **Resolved by the Sep 2026 review** — order reads go through the module's cache; no route/page reads an order straight from Prisma.

### Stats cache module
`src/lib/stats-cache.ts`. The dashboard statistics cache. Invalidation is owned by the Order cache module (stats derive from orders).

### Cache primitives
`src/lib/redis-cache.ts` (`createRedisCache(ttlMs, namespace)`) over `src/lib/cache.ts` (`createCache` in-memory fallback) and `src/lib/redis.ts`. The dual path is deliberate: Redis when `REDIS_URL` is set, in-memory fallback otherwise.

### Cache-ownership rule
1. A route never creates a cache inline — it imports an owned cache from the module that owns the concept.
2. Invalidation clears what the owning module owns — never a hardcoded string list in a central file.
3. Mutating an Order (or its status) invalidates Order caches **and** stats; mutating any catalogue entity invalidates the whole Catalogue.

### Catalogue write module — *seam*
`src/lib/catalogue-write.ts`. The write-side sibling of `product-read.ts` — owns the mutation policy shared by two or more admin write routes so it has one home instead of N copies: `generateUniqueSlug(base, ignoreId?)` (first free slug, `-2`, `-3`, …; `ignoreId` lets an update keep its own slug) and `assertGiftBoxNotOnBox(categoryId)` (throws a `statusCode`-bearing Error that `withAdmin` maps to 400). Route-field builders, soft delete, and the 409-referenced-category block stay inline in their single calling route — dedupe only when a second caller appears.

### Pricing module — *seam*
`src/lib/pricing.ts`. One money computation shared by the checkout preview and the server finalize. Takes flat priced lines (`{ price, quantity, sku? }`) + `stateCode` → `{ subtotal, shippingCost, totalAmount }`. Owns the ₹599 free-shipping threshold, the TN/non-TN charges, and the `0000`-SKU test-product override; absorbs `calcShippingCost`. Two real callers justify the seam. Decided Sep 2026: subtotal **includes gift-box prices** so paid == stored going forward (historical orders keep their stored totals); money stays rupee floats — integer-paise arithmetic and the exact paid==stored comparison belong to the Order seam; display formatting lives beside it in `src/lib/format.ts`. Gift-box bundling rules stay with the Order intake, not Pricing. The shared **order projections** live here too: `orderLineViews` (flatten parent + gift-box rows in render order — admin modal, confirmation, PDF invoice) and `shippingProgress(subtotal)` (the ₹599 → `{ remaining, percent, unlocked }` — cart card, nudge popup, and `useShippingNudge` all render it; no surface recomputes the threshold). **Resolved Sep 2026 review** — do not re-implement threshold progress or totals formatting in a surface. **ADR-0003 (Sep 2026):** the packing label and Excel export are deliberate *operator artifacts* with their own line rows — the label's are editable at pack time and flat by design, the export dumps stored rows verbatim; `orderLineViews` stays the one projection for surfaces that *render order money to a reader*, and no `editable` variant was added.

### Order intake module — *seam*
`src/lib/order-intake.ts`. Owns the **Order lifecycle policy** behind one interface:

- **Placement:** `parseCreateOrderInput` (intent validation → `OrderError`/400) + `placeOrder` (gift-box bundling rules, stock checks, atomic decrements, ADR-0002 pricing basis, persistence with snapshots + status history, all inside a serializable transaction).
- **Fulfilment:** `parseUpdateOrderStatusInput` + `transitionOrderStatus` (versioned optimistic concurrency, tracking gate at `shipped`, `validateTransition` against the flow — no skips, no leaving `rejected`/`delivered` — and stock restore on `rejected`, atomic in a transaction) **and the tracking write** `parseUpdateTrackingInput` + `setTrackingId` (versioned, same 404/409 taxonomy; a tracking ID is editable in any status — pre-printed on packaging, corrected on delivered — the `shipped` gate lives on the status transition). The tracking route is a thin adapter over `setTrackingId`, exactly like the status route; both fulfilment input schemas are the shared `UpdateOrderStatusInputSchema`/`UpdateTrackingInputSchema` in `schemas.ts` (no module-local twin).
- **Invariants & taxonomy:** `assertPaidAmountMatchesTotal` (paid paise == stored total) and the `OrderError` class both paths map to HTTP.

`POST /api/orders` and `PATCH /api/orders/[id]/status` are thin adapters: parse → module call → error mapping (plus gateway resolution / cache invalidation, which are adapter concerns). **Resolved by the Sep 2026 review (candidate 1); paid-amount invariant wired and fulfilment deepened the same month** — tests hit the module interface directly (`src/lib/__tests__/order-intake.test.ts`, `src/lib/__tests__/order-fulfilment.test.ts`); no HTTP harness.

### Order view module — *seam*
`src/lib/order-view.ts`. Owns the **read projection** of an Order — the one interface the confirmation page, the tracking results, the shared order-detail modal, and the PDF invoice consume. `toOrderView(order)` takes an order row with `items` + `statusHistory` and returns the `OrderView` (money as numbers, items carrying `parentOrderItemId` so `orderLineViews` nests gift boxes, `itemCount`, and the status history oldest-first). `orderTimeline(status, history?)` returns timeline entries from the **persisted** `OrderStatusHistory` when the surface carries it, falling back to the forward flow (`rejected` → one step) when it doesn't — so no surface re-derives the timeline from `ORDER_STATUS_FLOW`. **Resolved by the Sep 2026 review (candidate 1)** — before this, three surfaces projected the Order independently and disagreed: the tracking projection dropped `subtotal`/`shippingCost`/`parentOrderItemId`, so the shared modal rendered `₹NaN` and flattened gift boxes on the track surface, and the modal recomputed the timeline while the audit trail sat unused. Two rules survive: (1) no surface projects an Order row itself — read through `toOrderView`; (2) `OrderStatusHistory.notes` stay server-side and are never projected into a view (the tracking surface is unauthenticated). Tests hit the module interface (`src/__tests__/lib/order-view.test.ts`).

### API docs contract — *seam*
`src/lib/openapi-spec.ts` derives from `src/lib/api/schemas.ts` — the docs are **generated from the live contract, not typed beside it**. `openApi(schema)` (native `z.toJSONSchema(schema, { target: "openapi-3.0" })`, then Zod's `additionalProperties: false` dropped because Zod strips unknown keys rather than rejecting them) is the one Zod → OpenAPI step. Derived from it: the `GET /api/products` envelope, `GET /api/categories`, `GET /api/categories/latest`, `GET /api/category/{slug}/products`, both `GET /api/auth/me` responses, the `PATCH /api/orders/{id}/status` body, the `GET /api/track` response, and the `Product` component. Enum vocabularies are read from their source and never re-typed: `ORDER_STATUS_ENUM` ← `ORDER_STATUS_ALL`, `ROLE_ENUM` ← `SessionSchema.shape.role`, `BADGE_ENUM` ← the `ProductBadge` database enum. Request bodies that carry prose (create/update product, checkout) stay hand-written, and the `Order`/`OrderDetail` components stay hand-written because `OrderSchema` unions two endpoints' shapes. `src/__tests__/lib/openapi-contract.test.ts` pins documented shapes back to the schema tree. **Track shape derivation (round-3 review):** `TrackOrderResultSchema` = `OrderSchema.omit({ version: true }).extend({ itemCount: z.number().optional() })` — `itemCount` stays optional because the shared order-detail modal accepts `Partial<Order> & TrackOrderResult` and an admin Order row carries no count — and `/api/track` was the last hand-typed endpoint, now retired alongside the derived `Order`/`OrderDetail` siblings (its derived shape intentionally drops `format: uuid`/`date-time`, consistent with the others). **Resolved by the Sep 2026 review (candidate 5)** — do not hand-type a shape that has a Zod schema, and do not re-add a hand-copied enum.

### Admin route adapter — *seam*
`src/lib/admin-route.ts`. Owns **everything a mutating admin route must do around its policy**: the CSRF origin check, the session check (401), optional JSON body parsing (400 on invalid JSON), the shared error taxonomy (`statusCode`-bearing domain errors like `OrderError`/`RazorpayGatewayError` keep their status; Prisma `P2002` → 409 with route-specific copy via `errorMessages`; `P2025` → 404; anything else → 500 with the route's fallback), and the optional catalogue-refresh epilogue (`revalidateCatalogue: true` → `invalidateCatalogCaches` + the three public `revalidatePath` surfaces, only after a 2xx). Routes declare `withAdmin(handler, opts)`; the handler receives `{ request, admin, params, body }` and holds only the actual policy. **Resolved by the Sep 2026 pass-2 review (candidate A)** — migrated across products, categories, orders (GET/status/tracking), stats, and export. Do not re-suggest per-route guard consolidation; new admin mutations must use `withAdmin`. Public routes (`POST /api/orders`, auth, tracking lookup) are deliberately *not* wrapped — they have their own concerns (rate limits, no session). Tests: `src/lib/__tests__/admin-route.test.ts` hits the adapter interface directly.

### Product display module — *seam*
`src/lib/product-display.ts`. One home for the display transforms every customer and admin surface renders from: `stockHealth` (one low-stock threshold, `LOW_STOCK_MAX`), `primaryImage` (the **one picker**: primary gallery image → single image → the shared `IMAGE_UNAVAILABLE_PLACEHOLDER` — card/detail images, JSON-LD, and og/twitter all call it), and `productDisplayView` (price/compare/discount math + one badge-class map). The **load-failure half** lives in `src/components/ui/FallbackImage.tsx` — the one component every surface renders through: a broken src swaps to the same placeholder (tracked per-src, so a reused instance resets on src change) and an empty src fails upfront instead of throwing. No surface keeps its own `imgFailed` swap state or URL-validity gate. Created because the thresholds and pick had drifted across views (the low-stock cutoff was ≤3 on cards vs ≤5 on the detail page, and the detail page re-implemented the image pick). The detail read once surfaced a precomputed `primaryImageUrl`; the round-3 review deleted that shortcut so no surface can re-implement the pick. **Resolved Sep 2026 (round-3 review)** — one picker, one threshold, one discount formula. **Failure swap resolved Sep 2026 (round-4 review)** — one placeholder for null AND load failure.

### Cart wire projection module
`src/lib/cart-wire.ts`. The **one shape a cart crosses the boundary with** — cookie name/lifetime constants (`CART_COOKIE`, `CART_MAX_AGE`), the server-parsing wire schema `cartSchema` (UUID product ids, positive-int quantities, optional gift boxes), and `cartItemsToWire` (strip surprise gifts, reduce gift-box lines to ids). Both boundary sides import it — the server read (`cart-cookie.ts` parses `cartSchema`) and the client write (`CartProvider` serializes through `cartItemsToWire`) — so a wire change is one edit, and cookie I/O stays on each side (the server side is `next/headers`-bound and must never be imported by the client). Tests hit the projection interface directly (`src/__tests__/lib/cart-wire.test.ts`); the wire schema enforces RFC-4122 UUIDs (variant digit `[89ab]`) on both real cookies and test fixtures. **Resolved Sep 2026 (round-3 review)** — the wire contract is no longer declared twice.

### Checkout payment seam
`src/lib/hooks/useCheckoutPayment.ts`. The Razorpay browser capture as a testable seam: create the gateway order → load the script → open Standard Checkout → verify the signature → place the order through the caller's mutation, resolving a typed `RazorpayOutcome` (`ok` / `cancelled` / `failed` / `error`). The page keeps validation, toasts, and navigation; the sequence was previously ~90 inline lines in `app/order/page.tsx` with no seam to test through. `getErrorMessage` (shared page/hook error wording) lives in `src/lib/api/client.ts`. Tests hit the hook interface with a fake Razorpay constructor (`src/__tests__/lib/hooks/useCheckoutPayment.test.ts`). **Resolved Sep 2026 (round-3 review).**

### Design vocabulary

Terms from the codebase-design vocabulary, used exactly in architecture discussion:

- **Module** — a unit with an interface and an implementation. A **deep** module hides big complexity behind a small interface; a **shallow** module has interface ≈ implementation.
- **Interface** — what callers must know to use the module. **The interface is the test surface** — tests should exercise the interface, not the HTTP harness.
- **Seam** — a place where behavior can be swapped or intercepted; the boundary a deepening refactor targets.
- **Adapter** — a thin layer translating between the module interface and the outside world (e.g. HTTP handlers, a payment gateway client).
- **Leverage** — how much work a small amount of interface buys; deep modules are high-leverage.
- **Locality** — related things living together; the opposite of "bounce across eight files to understand one concept."
- **Deletion test** — would deleting this module *concentrate* complexity (deep, keep it) or just *move* it (shallow, merge it)? "Yes, concentrates" is the signal for a deepening opportunity.

## Open seams

Findings from the Aug 2026 architecture review, not yet addressed:

- **Order module** (candidate 1, *Strong*) — placement / fulfilment / payment logic lives inline in HTTP handlers; inventory knowledge is split; the payment flow lacks an amount-integrity invariant. **Placement resolved (Sep 2026):** deepened into the [Order intake module](#order-intake-module--seam) (`placeOrder` + `OrderError` + parse + paid-amount assertion). **Paid-amount invariant wired (Sep 2026):** razorpay placements verify the charged amount against the gateway server-side and the intake asserts paid == stored before persisting. **Fulfilment resolved (Sep 2026):** status transitions deepened into the same module (`transitionOrderStatus` + `validateTransition` + `parseUpdateOrderStatusInput`); `PATCH /api/orders/[id]/status` is a thin adapter. **No open remainder** for this candidate.
- **Pricing policy** (candidate 2, *Strong*) — shipping + total computed twice (checkout preview vs server finalize). **Decisions made (Sep 2026):** deepen into `src/lib/pricing.ts`; subtotal includes gift-box prices (paid == stored, forward); rupee floats; separate `src/lib/format.ts`. **Implemented:** `computePricing` in `src/lib/pricing.ts` is the single money computation and both callers consume it — the checkout preview (`app/order/page.tsx`) and the server finalize (the Order intake's `placeOrder`); ADR-0002 records the basis. No open remainder.
- **One contract, not four** (candidate 3, *Worth exploring*) — input contracts duplicated as server Zod, client Zod, and hand-rolled checkout rules. **Partially resolved (Aug 2026):** the 9× copy-pasted `.safeParse` 400 block in the API routes is now one shared helper, `validateOr400` in `src/lib/validate.ts`. **Checkout half resolved (Sep 2026):** the per-field checkout rules (name, email, 10-digit phone, 6-digit PIN, Indian state code) live once in `src/lib/checkout-fields.ts` (`CheckoutFields` map + `fieldIssue` helper), composed by the server intake's `CreateOrderSchema`, the client `CreateOrderInputSchema`, and the checkout page's step validation — one rule, one message, three surfaces. Non-checkout contracts (admin product/category payloads) remain server-Zod + client-Zod duplicates by design: their shapes and audiences differ enough that unifying them would add coupling without killing a bug class. Candidate closed.
- **Admin dashboard mesh** (candidate 5, *Speculative*) — six controller hooks behind a 25-key interface. **Partially resolved (Aug 2026):** the duplicated cache patching collapsed into `patchProductCache` / `removeProductFromCache` (one key-group list drives both admin lists and catalogue grids) and the controllers have direct hook tests. **Resolved (Sep 2026 review):** deepened into **panel-view modules** — `useAdminOrdersPanel`, `useAdminCataloguePanel`, `useAdminCategoriesPanel`, each co-located beside its lazy-loaded panel in `src/components/admin/`, each exposing a typed `{ data, loading, actions }` view-model and composing the existing query hooks + controller (whose direct tests are unchanged). `useAdminPageState` is now the aggregate only: session gate, active tab, stats/charts, and selected-order state (the page-level order-detail/tracking modals keep selection at the aggregate). Cache patching stays in `useAdminMutations`. Constraint respected: panels are `next/dynamic` with `ssr: false`, so the modules live in panel-side files, not the eager page bundle.

**Resolved:** Catalogue cache module (candidate 4) — done Aug 2026.
