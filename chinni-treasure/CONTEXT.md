# Chinni Treasure — Domain Glossary (CONTEXT.md)

Living vocabulary for architecture reviews and agents working in this codebase.
Architecture terms follow the codebase-design vocabulary (see [Design vocabulary](#design-vocabulary)).
Terms marked **seam** are names for good module boundaries — use them when talking about deepening opportunities.

## Domain concepts

| Term | Meaning | Where it lives |
|---|---|---|
| **Product** | The sellable unit. Has `sku`, `price`, `compareAtPrice` (MRP for strikethrough display), `stockQuantity`, `badge`, `visibleHostnames` (multi-domain filter), soft-delete (`deletedAt`), and multiple `ProductImage`s (one primary). | `prisma/schema.prisma` |
| **Category** | Product grouping with `slug`, `displayOrder`, `isActive`. Deleting is blocked while non-deleted products reference it (409). | `prisma/schema.prisma`, `app/api/categories/*` |
| **Catalogue** | The customer-facing listing surface: product listings, category pages, "latest per category", and recent products. Treated as **one concept** for caching — see [Catalogue cache module](#architecture-modules). | `app/api/products/*`, `app/api/categories/*`, `app/api/category/[slug]/products` |
| **Cart** | Guest cart: React Context + `localStorage`, synced to a server-side cookie for SSR. The mutators are **deep**: `addItem` returns `{ result, newTotal }` where `newTotal` is the authoritative post-add total computed from the committed state — callers never re-derive "total after this add" from a stale `getTotal()` (that stale read was the ₹0 shipping-nudge popup bug, fixed Sep 2026). The Cart module is the only place that knows its own asynchrony. The cart's boundary shapes are **three projections of one rule**, owned by the [Cart projections module](#cart-projections-module--seam) (`src/lib/cart-projections.ts`): the cookie wire (`cartItemsToWire` — schema, serializer, cookie name/lifetime), the money lines (`cartPricedLines` → the Pricing module's `PricedLine[]`), and the order-intake payload (`cartOrderItems`). Which lines cross a boundary — parents plus their gift boxes, never the surprise gift — is private to that module, so a boundary change is one edit, never two coordinated ones. | `src/components/cart/CartProvider.tsx`, `src/lib/cart-cookie.ts` |
| **Checkout** | The multi-step order page (details → delivery → payment & review). Computes a client-side preview of totals. The Razorpay capture sequence is a **seam**: `useCheckoutPayment` owns create-order → open Standard Checkout → verify signature → place (through the page's mutation) and resolves a typed outcome — the page keeps validation, toasts, and navigation. | `app/order/page.tsx`, `src/lib/hooks/useCheckoutPayment.ts` |
| **Pricing** | The money module: subtotal (parent lines **plus** gift-box lines), shipping (₹599 free threshold; ₹150 TN / ₹200 elsewhere; `0000`-SKU test product ships free), and total. Carries rupee floats; the exact paid==stored invariant is owned by the Order seam. Decided Sep 2026: subtotal includes gift-box prices — paid == stored going forward. | `src/lib/pricing.ts` |
| **Order** | The aggregate: `orderNumber`, customer + address, `status`, `version` (optimistic concurrency), `subtotal`/`shippingCost`/`totalAmount`, `transactionId`, `trackingId`, `items`, `statusHistory`. Surfaces render the **Order view** projection, never the row — see [Order view module](#order-view-module--seam). | `prisma/schema.prisma` |
| **OrderItem** | Price/name snapshot of a product at purchase time; `productId` is nullable (SetNull when the product is deleted). | `prisma/schema.prisma` |
| **Fulfilment** | The status flow: `pending → approved → packaging → shipped → delivered`, with `rejected` (restores stock). Tracking ID required at `shipped`; transitions are versioned and **validated against the flow** (no skips, no leaving terminal states). Owned by the Order intake module's fulfilment half. | `src/lib/order-intake.ts` (`transitionOrderStatus`), `src/lib/constants.ts` (`ORDER_STATUS_FLOW`) |
| **Payment** | The Razorpay gateway flow, deepened into one module (`src/lib/razorpay-server.ts`): `createGatewayOrder` (order creation for Standard Checkout — rupees in, paise conversion and the minimum-amount policy inside), `verifyCheckoutSignature` (HMAC-SHA256 in constant time), and `acceptPlacementPayment` (the paid==stored prologue: authoritative snapshot from `payments.fetch` that must belong to the given order and be `captured`/`authorized`). Routes are thin adapters — parse → module call → error mapping via `RazorpayGatewayError`; `transactionId` is recorded on the Order and `placeOrder` asserts paid paise == stored total (ADR-0002) before persisting; manual bank-transfer placements skip the gateway check. | `src/lib/razorpay-server.ts`, `src/lib/order-intake.ts` |
| **Inventory** | `stockQuantity` on Product. Deducted atomically at order placement (serializable transaction), restored on rejection. | `src/lib/order-intake.ts` (`placeOrder`) |
| **Admin** | The dashboard surface: JWT session in an HttpOnly cookie (`proxy.ts` guards `/admin/*`), roles `admin` / `super_admin`, stats + charts, catalogue/category/order CRUD. | `app/admin/*`, `src/lib/hooks/useAdmin*Controller.ts` |

## Architecture modules

These are **deep modules** — small interfaces, big hidden implementations — that own a concept. Future reviews should deepen around these seams, not re-litigate them.

### Catalogue cache module — *seam*
`src/lib/catalogue-cache.ts`. Owns **all six catalogue caches** (`products`, `catindex`, `categories`, `catlatest`, `catpage`, `giftboxes`) and exports `invalidateCatalogCaches()`, which clears exactly what the module owns (the namespace in Redis via SCAN+DEL **plus** the local in-memory fallback). Routes import their cache from this module; they never call `createRedisCache` themselves. **Resolved by the Aug 2026 architecture review** — do not re-suggest a hardcoded namespace list. The `catindex` cache holds the full active-product list per hostname so public catalogue searches filter in memory instead of querying Postgres per request. The index query surface (`queryCatalogueIndex`, filter/sort/page over `catindex`) lives in this module too, so the route only parses, calls, and envelopes. `SORT_OPTIONS` — the **one catalogue order contract** — lives here too: every entry is a complete orderBy (in-stock first, then the chosen field, then id desc), consumed verbatim by the `/api/products` status branch (`listProductsForQuery` in `product-read.ts`), the category pages, and the in-memory `catIndex` comparator (which walks the same arrays). Changing a sort rule means editing `SORT_OPTIONS`; no route re-declares an order. **Resolved by the Sep 2026 review** — do not re-add per-route orderBy mirrors.

### Catalogue read module — *seam*
`src/lib/product-read.ts`. The SQL read surface for the catalogue: catalogue SSR (`listCatalogue`), category pages (`listByCategory`, plus the public view coercion `toProductView`/`toCatalogueProductView`), active-category options (`loadActiveCategories`), and gift-box lookup (`listGiftBoxes`). It imports the shared `SORT_OPTIONS` rather than declaring its own `DEFAULT_ORDER`; `CATEGORY_SORT_MAP` is now just the category page's allowed-key allow-list pointing at the shared table. **Resolved by the Sep 2026 review** — an ordering rule belongs in `SORT_OPTIONS` or it doesn't exist. Both new surfaces cache through the module-owned caches: `listCatalogue` keys `productsCache` by `host:list:categoryId` (no search — SSR search never reaches the fetch, so no key), and `loadActiveCategories` reads/writes the `categoriesCache` `active` key shared with the public `/api/categories` handler. The SSR catalogue page stopped hand-rolling cache get/set and bespoke `cat:`/`cats:` keys; it reads through these surfaces. **Resolved by the Sep 2026 review** — catalogue SSR reads go through one owned-cache surface; invalidation reaches the page, search stays out of cache keys. Two further surfaces belong here (Sep 2026 pass-3 review): `listProductsForQuery(hostname, query)` is the single `/api/products` list read — it owns the status gate (`active` → the in-memory index; `all`/`inactive` → Postgres through `productsCache`), the where-builder and the envelope, leaving the route to parse the URL and enforce the session; and `getProductDetail(id, hostname)` is the product-detail read — module-owned `unstable_cache` under the `product-detail` tag, with the active / soft-deleted / domain-visibility checks running **outside** the cache (one host's visibility verdict must never be served to another) and the returned view carrying the raw image pieces (`imageUrl` + `images`) — the primary pick is left to the display seam's `primaryImage()`, so JSON-LD, og/twitter, and the gallery all read the one picker's answer. (The precomputed `primaryImageUrl` shortcut was retired in the round-3 review — it duplicated the picker.) **Security rule:** `isActive=all|inactive` on `GET /api/products` requires an admin session and answers `private, no-store` — the gate lives at the route seam, so no branch can forget it. **Resolved by the Sep 2026 pass-3 review** — one list read, one detail read, no page-private Prisma cache, no anonymous enumeration of inactive products. **Read-through completed (Sep 2026 architecture review, candidate 3):** `listByCategory` now owns the `catPageCache` key (`host:slug:page:limit:sort`) and its hit/miss branch — the route is parse → call → envelope, and the SSR category page shares the same entries — and `listGiftBoxes` owns the `giftBoxCache` `all` key. A missing/inactive category is deliberately **not** cached, so a 404 cannot outlive its cause.

### Order cache module — *seam*
`src/lib/order-cache.ts`. Owns the order-detail cache (`order`) and the tracking cache (`track`), plus `invalidateOrderCache(orderId?)`. Order-derived **stats are cleared here too** — on any order mutation (status change / tracking update), the dashboard cache must refresh. Its two read surfaces are `getOrderDetail(id)` (cache-first, Prisma fill on a miss, 30s TTL), used by the `/api/orders/[id]` route and the SSR confirmation page — which dropped its `revalidate = 30` build-time ISR (unreachable by any cache invalidation) for `force-dynamic` + this read surface — and `getTrackedOrders(orderId, phone)` (**added Sep 2026 architecture review, candidate 3**), which owns the tracking key, the hit/miss branch, the lookup's own 400 (no id *and* no phone), and the projection through `formatOrderResults`; `/api/track` only rate-limits, parses, and envelopes. **Resolved by the Sep 2026 review** — order reads go through the module's cache; no route/page reads an order straight from Prisma. (Round-6 review: this was true of the detail and tracking surfaces but **false of the admin list** — see below. The rule now holds for all three.)

**The admin list read (round-6 review).** `src/lib/order-read.ts` is the module those two surfaces are built on, and it is the order-side sibling of `product-read.ts` — it holds `buildTrackCacheKey`, `queryOrdersByOrderId`, `queryOrdersByPhone`, `formatOrderResults`, and now `listOrdersForAdmin`. The admin orders list used to be the *one* order surface that reached past this module into Prisma: `GET /api/orders` ran `prisma.order.findMany` + `count` inline, which made the "no route reads an order straight from Prisma" claim above false, and the codebase over-trusted it. `listOrdersForAdmin` owns the where/status cast, the item include and the sequential (not `Promise.all`) pair of queries, so the route is parse → call → envelope like every other order adapter. `AdminOrderRow` deliberately keeps `adminNotes`: the admin list is authenticated, and CONTEXT's rule that status-history notes never enter a view exists because *the tracking surface* is unauthenticated, not because notes are secret. `ORDER_SORTS` stays in the route — it is the dashboard's own column order, not a shared catalogue contract, so it is not merged into `SORT_OPTIONS`.

### Stats cache module
`src/lib/stats-cache.ts`. The dashboard statistics cache **and its read surface** `getDashboardStats()` (cache-first, `computeDashboardStats` fill on a miss) — added Sep 2026 (architecture review, candidate 3) so `/api/stats` is envelope + error mapping only. Invalidation is owned by the Order cache module (stats derive from orders).

### Cache primitives
`src/lib/redis-cache.ts` (`createRedisCache(ttlMs, namespace)`) over `src/lib/cache.ts` (`createCache` in-memory fallback) and `src/lib/redis.ts`. The dual path is deliberate: Redis when `REDIS_URL` is set, in-memory fallback otherwise.

### Cache-ownership rule
1. A route never creates a cache inline — it imports an owned cache from the module that owns the concept.
2. Invalidation clears what the owning module owns — never a hardcoded string list in a central file. **Extended (Sep 2026 architecture review, candidate 3):** a route never *keys* a cache either — the key, the hit/miss branch and the response's own validation live behind the owning module's read surface, so the adapter holds only parse/envelope/error mapping.
3. Mutating an Order (or its status) invalidates Order caches **and** stats; mutating any catalogue entity invalidates the whole Catalogue.

### Catalogue write module — *seam*
`src/lib/catalogue-write.ts`. The write-side sibling of `product-read.ts` — owns the mutation policy shared by two or more admin write routes so it has one home instead of N copies: `generateUniqueSlug(base, ignoreId?)` (first free slug, `-2`, `-3`, …; `ignoreId` lets an update keep its own slug) and `assertGiftBoxNotOnBox(categoryId)` (throws a `statusCode`-bearing Error that `withAdmin` maps to 400). Route-field builders, soft delete, and the 409-referenced-category block stay inline in their single calling route — dedupe only when a second caller appears.

### Pricing module — *seam*
`src/lib/pricing.ts`. One money computation shared by the checkout preview and the server finalize. Takes flat priced lines (`{ price, quantity, sku? }`) + `stateCode` → `{ subtotal, shippingCost, totalAmount }`. Owns the ₹599 free-shipping threshold, the TN/non-TN charges, and the `0000`-SKU test-product override; absorbs `calcShippingCost`. Two real callers justify the seam. Decided Sep 2026: subtotal **includes gift-box prices** so paid == stored going forward (historical orders keep their stored totals); money stays rupee floats — integer-paise arithmetic and the exact paid==stored comparison belong to the Order seam; display formatting lives beside it in `src/lib/format.ts`. Gift-box bundling rules stay with the Order intake, not Pricing. The shared **order projections** live here too: `orderLineViews` (flatten parent + gift-box rows in render order — admin modal, confirmation, PDF invoice) and `shippingProgress(subtotal)` (the ₹599 → `{ remaining, percent, unlocked }` — cart card, nudge popup, and `useShippingNudge` all render it; no surface recomputes the threshold). **Resolved Sep 2026 review** — do not re-implement threshold progress or totals formatting in a surface. **ADR-0003 (Sep 2026):** the packing label and Excel export are deliberate *operator artifacts* with their own line rows — the label's are editable at pack time and flat by design, the export dumps stored rows verbatim; `orderLineViews` stays the one projection for surfaces that *render order money to a reader*, and no `editable` variant was added.

### Order intake module — *seam*
`src/lib/order-intake.ts`. Owns the **Order lifecycle policy** behind one interface:

- **Placement:** `parseCreateOrderInput` (intent validation → `OrderError`/400) + `placeOrder` (gift-box bundling rules, stock checks, atomic decrements, ADR-0002 pricing basis, persistence with snapshots + status history, all inside a serializable transaction).
- **Fulfilment:** `parseUpdateOrderStatusInput` + `transitionOrderStatus` (versioned optimistic concurrency, tracking gate at `shipped`, `validateTransition` against the flow — no skips, no leaving `rejected`/`delivered` — and stock restore on `rejected`, atomic in a transaction) **and the tracking write** `parseUpdateTrackingInput` + `setTrackingId` (versioned, same 404/409 taxonomy; a tracking ID is editable in any status — pre-printed on packaging, corrected on delivered — the `shipped` gate lives on the status transition). The tracking route is a thin adapter over `setTrackingId`, exactly like the status route; both fulfilment input schemas are the shared `UpdateOrderStatusInputSchema`/`UpdateTrackingInputSchema` in `schemas.ts` (no module-local twin).
- **Invariants & taxonomy:** `assertPaidAmountMatchesTotal` (paid paise == stored total) and the `OrderError` class both paths map to HTTP.

`POST /api/orders` and `PATCH /api/orders/[id]/status` are thin adapters: parse → module call → error mapping (plus gateway resolution / cache invalidation, which are adapter concerns). **Resolved by the Sep 2026 review (candidate 1); paid-amount invariant wired and fulfilment deepened the same month** — tests hit the module interface directly (`src/__tests__/lib/order-intake.test.ts`, `src/__tests__/lib/order-fulfilment.test.ts`); no HTTP harness.

### Order view module — *seam*
`src/lib/order-view.ts`. Owns the **read projection** of an Order — the one interface the confirmation page, the tracking results, the shared order-detail modal, and the PDF invoice consume. `toOrderView(order)` takes an order row with `items` + `statusHistory` and returns the `OrderView` (money as numbers, items carrying `parentOrderItemId` so `orderLineViews` nests gift boxes, `itemCount`, and the status history oldest-first). `orderTimeline(status, history?)` returns timeline entries from the **persisted** `OrderStatusHistory` when the surface carries it, falling back to the forward flow (`rejected` → one step) when it doesn't — so no surface re-derives the timeline from `ORDER_STATUS_FLOW`. **Resolved by the Sep 2026 review (candidate 1)** — before this, three surfaces projected the Order independently and disagreed: the tracking projection dropped `subtotal`/`shippingCost`/`parentOrderItemId`, so the shared modal rendered `₹NaN` and flattened gift boxes on the track surface, and the modal recomputed the timeline while the audit trail sat unused. Two rules survive: (1) no surface projects an Order row itself — read through `toOrderView`; (2) `OrderStatusHistory.notes` stay server-side and are never projected into a view (the tracking surface is unauthenticated). Tests hit the module interface (`src/__tests__/lib/order-view.test.ts`).

### API docs contract — *seam*
`src/lib/openapi-spec.ts` derives from `src/lib/api/schemas.ts` — the docs are **generated from the live contract, not typed beside it**. `openApi(schema)` (native `z.toJSONSchema(schema, { target: "openapi-3.0" })`, then Zod's `additionalProperties: false` dropped because Zod strips unknown keys rather than rejecting them) is the one Zod → OpenAPI step. Derived from it: the `GET /api/products` envelope, `GET /api/categories`, `GET /api/categories/latest`, `GET /api/category/{slug}/products`, both `GET /api/auth/me` responses, the `PATCH /api/orders/{id}/status` body, the `GET /api/track` response, and the `Product` component. Enum vocabularies are read from their source and never re-typed: `ORDER_STATUS_ENUM` ← `ORDER_STATUS_ALL`, `ROLE_ENUM` ← `SessionSchema.shape.role`, `BADGE_ENUM` ← the `ProductBadge` database enum. Request bodies that carry prose (create/update product, checkout) stay hand-written, and the `Order`/`OrderDetail` components stay hand-written because `OrderSchema` unions two endpoints' shapes. `src/__tests__/lib/openapi-contract.test.ts` pins documented shapes back to the schema tree. **Track shape derivation (round-3 review):** `TrackOrderResultSchema` = `OrderSchema.omit({ version: true }).extend({ itemCount: z.number().optional() })` — `itemCount` stays optional because the shared order-detail modal accepts `Partial<Order> & TrackOrderResult` and an admin Order row carries no count — and `/api/track` was the last hand-typed endpoint, now retired alongside the derived `Order`/`OrderDetail` siblings (its derived shape intentionally drops `format: uuid`/`date-time`, consistent with the others). **Resolved by the Sep 2026 review (candidate 5)** — do not hand-type a shape that has a Zod schema, and do not re-add a hand-copied enum.

### Admin route adapter — *seam*
`src/lib/admin-route.ts`. Owns **everything a mutating admin route must do around its policy**: the CSRF origin check, the session check (401), optional JSON body parsing (400 on invalid JSON), the shared error taxonomy (`statusCode`-bearing domain errors like `OrderError`/`RazorpayGatewayError` keep their status; Prisma `P2002` → 409 with route-specific copy via `errorMessages`; `P2025` → 404; anything else → 500 with the route's fallback), and the optional catalogue-refresh epilogue (`revalidateCatalogue: true` → `invalidateCatalogCaches` + the three public `revalidatePath` surfaces, only after a 2xx). Routes declare `withAdmin(handler, opts)`; the handler receives `{ request, admin, params, body }` and holds only the actual policy. **Resolved by the Sep 2026 pass-2 review (candidate A)** — migrated across products, categories, orders (GET/status/tracking), stats, and export. Do not re-suggest per-route guard consolidation; new admin mutations must use `withAdmin`. Public routes (`POST /api/orders`, auth, tracking lookup) are deliberately *not* wrapped — they have their own concerns (rate limits, no session). Tests: `src/__tests__/lib/admin-route.test.ts` hits the adapter interface directly.

### Product display module — *seam*
`src/lib/product-display.ts`. One home for the display transforms every customer and admin surface renders from: `stockHealth` (one low-stock threshold, `LOW_STOCK_MAX`), `primaryImage` (the **one picker**: primary gallery image → single image → the shared `IMAGE_UNAVAILABLE_PLACEHOLDER` — card/detail images, JSON-LD, and og/twitter all call it), and `productDisplayView` (price/compare/discount math + one badge-class map). The **load-failure half** lives in `src/components/ui/FallbackImage.tsx` — the one component every surface renders through: a broken src swaps to the same placeholder (tracked per-src, so a reused instance resets on src change) and an empty src fails upfront instead of throwing. No surface keeps its own `imgFailed` swap state or URL-validity gate. Created because the thresholds and pick had drifted across views (the low-stock cutoff was ≤3 on cards vs ≤5 on the detail page, and the detail page re-implemented the image pick). The detail read once surfaced a precomputed `primaryImageUrl`; the round-3 review deleted that shortcut so no surface can re-implement the pick. **Resolved Sep 2026 (round-3 review)** — one picker, one threshold, one discount formula. **Failure swap resolved Sep 2026 (round-4 review)** — one placeholder for null AND load failure. **One product shape resolved Sep 2026 (architecture review, candidate 4)** — the Zod contract is the only display product shape: `ProductCoreSchema` → `Product` / `CatalogueProduct`, plus the exported `ProductImage`. `ProductCard` takes `CatalogueProduct` and `useAddToCart` takes it too, so the `ProductData` / `ProductImageData` / `AddableProduct` twins are gone and a schema field can no longer stop reaching the card without a type error. The read module's `ProductDetailView` is the one deliberate narrowing (`imageUrl`/`description` non-null, `images` required — the detail read coerces them), and `ProductDetailsContent` consumes that type rather than declaring its own copy. One residual stays named: `src/lib/product-read.ts`'s exported `ProductView` / `CatalogueProductView` are structural copies of `Product` / `CatalogueProduct` (no external importers) — typing them as the schema types is a read-module change, not a display one.

### Gallery & Lightbox module — *seam*
`src/components/ui/ImageLightbox.tsx` (the deep core) + `src/components/ui/ProductImageGallery.tsx` (the composition). One home for **how a product image is viewed** — the Product display module owns *which* images (`primaryImage`, and `imageUrls(product)` for the full ordered list); this module owns *how they render*. The core `<ImageLightbox images initialIndex onClose zoom? onIndexChange?>` owns navigation (prev/next with wrap), the keyboard contract (ArrowLeft/ArrowRight/Escape **while open**, and never while an editable holds focus), the counter, the empty/degraded states, and every failure swap through `FallbackImage`. The old customer gallery's open-page arrow nav stays as that page's own local listener — a named exception the composition keeps, so the core's contract remains lightbox-only. Zoom (wheel + buttons + clamp + reset) is core behavior behind an opt-in `zoom` prop, not a surface-private extra. `<ProductImageGallery>` is a thin composition that owns the thumbnail strip and the main-image stage and opens the core; the admin catalogue lightbox and the product-form lightbox render the core directly (`imageUrls(product)` from the Product display module hands over the list — a viewer never re-picks which images exist), and overlay scaffold/focus behavior is the Modal module's concern, not this one's. Replaces three independent viewers that had already disagreed about failure handling — the detail gallery kept its own `failedImages` set, regressing the round-4 "no surface keeps its own swap state" rule on the biggest image surface. Tests hit the module interface (keyboard nav, wrap-around, zoom clamp, failure states) — `src/__tests__/components/ui/ImageLightbox.test.tsx`. **Resolved Sep 2026 (architecture review, candidate 1).**

### Cart projections module — *seam*
`src/lib/cart-projections.ts`. The **one home for what a cart becomes when it crosses a boundary**, and therefore the one home for the rule that decides which lines carry money. Three encoders, one private rule (`billableItems` — parents and their gift boxes, never the surprise gift):

- **`cartItemsToWire`** — the cookie boundary: cookie name/lifetime constants (`CART_COOKIE`, `CART_MAX_AGE`), the server-parsing wire schema `cartSchema` (RFC-4122 UUIDs, positive-int quantities, optional gift boxes), surprise gifts stripped and gift-box lines reduced to ids. Its input (`WireCartLine`) is deliberately **price-free**.
- **`cartPricedLines`** — the money boundary: flat `PricedLine[]` for the Pricing module's `computePricing`, each parent line first (carrying its `sku`, which the `0000` test-product shipping rule needs) then that parent's gift-box lines. It returns lines, never a sum — `computePricing` stays the one place money is computed, and `CartProvider` sums the projection for its own total.
- **`cartOrderItems`** — the intake boundary: the `POST /api/orders` payload rows (`id` keys, typed as `CreateOrderRequest["items"]`).

Both boundary sides import it — the server read (`cart-cookie.ts` parses `cartSchema`) and the client write (`CartProvider` serializes through `cartItemsToWire`) — so a boundary change is one edit, and cookie I/O stays on each side (the server side is `next/headers`-bound and must never be imported by the client). The two input shapes are deliberate: `WireCartLine` carries no prices because that boundary reads none, while `BillableCartLine` carries `price`/`sku` for the two money-bearing boundaries — one widened shape would make the wire contract appear to depend on fields it never uses. Tests hit the encoders directly (`src/__tests__/lib/cart-projections.test.ts`), including a cross-encoder test that the money and intake projections select the same parents. **Resolved Sep 2026 (round-3 review)** — the wire contract is no longer declared twice. **Deepened Sep 2026 (architecture review, candidate 2)** — the billable-lines rule had three homes (`CartProvider.computeItemsTotal`, the checkout page's `pricedLines`, `useCheckoutForm`'s `orderPayload`) and now has one, so the module is named for the concept instead of for one of its three boundaries. The two *count* surfaces deliberately stay out: `CartProvider.getCount` counts units and `OrderSummaryCard`'s display count counts lines — different quantities — so neither maps onto an encoder here; if a third count appears, that is the signal to deepen.

### Checkout payment seam
`src/lib/hooks/useCheckoutPayment.ts`. The Razorpay browser capture as a testable seam: create the gateway order → load the script → open Standard Checkout → verify the signature → place the order through the caller's mutation, resolving a typed `RazorpayOutcome` (`ok` / `cancelled` / `failed` / `error`). The page keeps validation, toasts, and navigation; the sequence was previously ~90 inline lines in `app/order/page.tsx` with no seam to test through. `getErrorMessage` (shared page/hook error wording) lives in `src/lib/api/client.ts`. Tests hit the hook interface with a fake Razorpay constructor (`src/__tests__/lib/hooks/useCheckoutPayment.test.ts`). **Resolved Sep 2026 (round-3 review).**

### Add-to-cart flow module — *seam*
`src/lib/hooks/useAddToCart.ts`. The **whole "add this product" lifecycle**, not just the add: an eligible product (`allowGiftBoxBundling`, and not itself a Gift Box) opens the gift-box modal instead of adding, and the modal's confirm / skip / close resolve back into the same cart write. The interface is two things — `handleAdd` for a product card's Add button, and `giftBox`, the ready-made `GiftBoxModal` props bundle a page renders as `{giftBox && <GiftBoxModal {...giftBox} />}` (or `null`). Both catalogue and category pages consume exactly that and keep no modal state; the flow's product mapping, its `as unknown as T` re-shape (the modal hands back a slim product, so stock is forced to 1), and the empty-list-means-undefined rule are private. Two facts earn the seam: the Cart module returns the authoritative post-add `newTotal` (the stale-read ₹0 nudge bug is structurally impossible through this call), and the old `open` flag was vestigial — the modal only ever rendered when a product was set, so the bundle's `open` is always true and the state is gone. **Resolved Sep 2026 (round-5 review, candidate 1)** — the two page copies (~45 lines each, line-for-line twins) are deleted; a new surface renders the bundle and nothing else. Tests hit the hook through the pages' behaviour (`GiftBoxModal.test.tsx`, `catalogue-pagination.test.tsx`) plus `CartProvider.test.tsx` for the cart write.

### Design vocabulary

Terms from the codebase-design vocabulary, used exactly in architecture discussion:

- **Module** — a unit with an interface and an implementation. A **deep** module hides big complexity behind a small interface; a **shallow** module has interface ≈ implementation.
- **Interface** — what callers must know to use the module. **The interface is the test surface** — tests should exercise the interface, not the HTTP harness.
- **Seam** — a place where behavior can be swapped or intercepted; the boundary a deepening refactor targets.
- **Adapter** — a thin layer translating between the module interface and the outside world (e.g. HTTP handlers, a payment gateway client).
- **Leverage** — how much work a small amount of interface buys; deep modules are high-leverage.
- **Locality** — related things living together; the opposite of "bounce across eight files to understand one concept."
- **Deletion test** — would deleting this module *concentrate* complexity (deep, keep it) or just *move* it (shallow, merge it)? "Yes, concentrates" is the signal for a deepening opportunity.

Findings from the Aug 2026 architecture review, not yet addressed:

- **Order module** (candidate 1, *Strong*) — placement / fulfilment / payment logic lives inline in HTTP handlers; inventory knowledge is split; the payment flow lacks an amount-integrity invariant. **Placement resolved (Sep 2026):** deepened into the [Order intake module](#order-intake-module--seam) (`placeOrder` + `OrderError` + parse + paid-amount assertion). **Paid-amount invariant wired (Sep 2026):** razorpay placements verify the charged amount against the gateway server-side and the intake asserts paid == stored before persisting. **Fulfilment resolved (Sep 2026):** status transitions deepened into the same module (`transitionOrderStatus` + `validateTransition` + `parseUpdateOrderStatusInput`); `PATCH /api/orders/[id]/status` is a thin adapter. **No open remainder** for this candidate.
- **Pricing policy** (candidate 2, *Strong*) — shipping + total computed twice (checkout preview vs server finalize). **Decisions made (Sep 2026):** deepen into `src/lib/pricing.ts`; subtotal includes gift-box prices (paid == stored, forward); rupee floats; separate `src/lib/format.ts`. **Implemented:** `computePricing` in `src/lib/pricing.ts` is the single money computation and both callers consume it — the checkout preview (`app/order/page.tsx`) and the server finalize (the Order intake's `placeOrder`); ADR-0002 records the basis. - **One contract, not four** (candidate 3, *Worth exploring*) — input contracts duplicated as server Zod, client Zod, and hand-rolled checkout rules. **Partially resolved (Aug 2026):** the 9× copy-pasted `.safeParse` 400 block in the API routes is now one shared helper, `validateOr400` in `src/lib/validate.ts`. **Checkout half resolved (Sep 2026):** the per-field checkout rules (name, email, 10-digit phone, 6-digit PIN, Indian state code) live once in `src/lib/checkout-fields.ts` (`CheckoutFields` map + `fieldIssue` helper), composed by the server intake's `CreateOrderSchema`, the client `CreateOrderInputSchema`, and the checkout page's step validation — one rule, one message, three surfaces.
